# SM120 Level-3 抢占：能力、缺陷与适用边界的全面评估

日期：2026-11-27　　范围：RTX 5060（GB206，30 SM，驱动桌面）、RTX 5080（GB203，84 SM，无显示）；分支 `phase3-def20-production-testing`。

本文对照 XSched 论文（OSDI'25，`xsched/docs/xsched-osdi25.pdf`）的模型，重新审视本项目 Level-3（Trap 引擎，Mode 5）的能力、缺陷、安全边界与生产适用性。每条结论标注证据等级：

- **【实测】**：有可复现的测量或日志（证据目录见文末）；
- **【推断】**：由实测数据与代码事实推出，但没有直接观察到硬件内部行为；
- **【推测】**：与现象相符的假设，未验证；
- **【未验证】**：尚无数据。

---

## 0. 结论摘要

1. **能力**【实测】：在单个 CUDA 上下文内，Level-3 可以在内核**执行中途**挂起任意（含非幂等）内核并原位恢复，挂起延迟与内核时长无关（驱逐 50–120 µs，恢复 30–330 µs）；在 LP 内核占满 SM 时，HP 尾延迟有界（0.8–2.6 ms，而 native 随 LP 内核增长到 12.7–26.6 ms、同步 Level-1 到 368 ms）。透明部署下（两个不改代码的 vLLM 进程）HP 端到端 P50 30.0 ms ≈ 独占 30.5 ms，P99 30.5–30.8 ms（Level-1 66.2 ms），LP 保留 88–93% 吞吐，结果全部一致。
2. **最主要的边界：Trap 与上下文时间片的冲突**【实测 + 推断】。BAR0 脉冲是全 GPU 的；GPU 在多个上下文（进程）之间按时间片切换时，**切换本身也经由 Trap 处理程序完成**。一个上下文的线程束正在执行我们的处理程序代码时，若 GPU 要切换上下文，切换可能无法在超时内完成 → Xid 109（`CTX SWITCH TIMEOUT`），驱动重置该上下文的通道（进程收到 CUDA 719）。不在 XSched 管理下、没有我们处理程序的上下文被脉冲打到，则直接出错（Xid 31 / Xid 109）。
3. **准确的安全条件**：不是“全局只有一个上下文”，而是**在每个 Trap 窗口（发脉冲到驱逐完成、恢复波次执行期间）内，GPU 上没有其他上下文有可运行的工作**。同一进程内任意多条流天然满足；多个 XSched 进程由就绪门控 + `xserver` 的 Level-3 轮换满足；不受 XSched 管理的上下文无法被协调，因此一旦检测到就**不发脉冲**（退化为 Level-1）。
4. **硬件限制**【实测】：寄存器文件被分配到最后一个寄存器的 SM 不接受 Trap（DEF-34）；这类内核只能在内核边界挂起。在 vLLM 7B-AWQ 中占 Trap 托管内核的 19%。
5. **不支持（退化为 Level-1 边界）的特性**：协作启动、线程块 Cluster（+DSMEM）、硬件 mbarrier（`SYNCS`，TMA 流水线依赖它）、不可展平的 CUDA Graph。当前软件栈（PyTorch / vLLM 0.34 / sm_120）上实测几乎不出现；新一代内核（TMA、warp 专用化、Cluster）普及后会成为主要的覆盖缺口【推断】。
6. **生产可用性判断**：在**专用 GPU + 所有租户都在 XSched 下 + 使用 `xserver`** 的前提下，Level-3 可安全使用，且已在端到端 vLLM 场景验证；共享 GPU（其他用户的作业、Kubernetes 时间片共享）、驱动显示器的 GPU 上，Level-3 自动退化为 Level-1，不会伤害其他租户，但也失去中途抢占能力。本实现依赖未公开的驱动内部结构与 BAR0 寄存器，属于研究原型而非可直接交付的产品组件（§8）。

## 1. 与论文模型的对照

### 1.1 论文的多级模型与 NVIDIA 实现

论文把抢占能力分为三级：Lv1 只控制命令的提交；Lv2 让已提交但未执行的命令失效（NVIDIA 上用二进制插桩的 Guardian：内核开头检查标志，置位则立即退出）；Lv3 中断正在执行的命令并能恢复。NVIDIA 上的 Lv3 有两种实现（论文 §6.3）：

- **TSG 方式**：把要抢占的进程的时间片设为 0、恢复时还原。“由于中断作用于整个 TSG，只能用于进程间调度。”状态保存由硬件上下文切换完成。
- **队列方式**：通过一个调试用 ioctl 写 GPU 控制寄存器，GPU“立即停住所有正在运行的内核并调用 Trap 处理程序”；XSched 扩展处理程序识别自己的中断，**中止**目标内核，其余内核恢复执行。“NVIDIA GPU 不提供从中断点恢复被中止内核的支持”，因此**只抢占幂等内核**，从头重跑；幂等性**人工标注**。

论文的“讨论与局限”一节列出：主动执行型设备、单命令任务（如 CUDA Graph，需要 Lv3 或切分任务）、显存充足假设、不可信租户（恶意租户可绕过 XSched）。**论文没有讨论 Trap 与上下文时间片切换的冲突、非 XSched 上下文被中断、寄存器文件占满不接受 Trap 等问题**（就其公开文本而言）。

### 1.2 本项目的位置

| 维度 | 论文（Volta / Ampere） | 本项目（Blackwell sm_120） |
|---|---|---|
| 中断触发 | 调试 ioctl 写控制寄存器 | 直接映射 BAR0 写 STOP_TRIGGER（root 或 `xsched-bar0d` 代理） |
| 被中断内核的处理 | 中止，幂等内核从头重跑 | **Mode 5**：保存整个 CTA 的寄存器、共享内存、屏障、局部内存，恢复波次原位恢复——**支持非幂等内核** |
| 未开始的 CTA | Guardian 退出（Lv2） | Guardian 排空（State C），恢复时重放 |
| 粒度 | 队列（hwQueue） | 队列（每条流一个控制块）；另有上下文级 Context CILP 后端（≈ 论文的 TSG 方式） |
| 处理程序复杂度 | 识别中断并退出（短） | 9 个代码洞，含 9 处 CTA 级 `BAR.SYNC.TRAP`、整 CTA 状态保存（长） |

Mode 5 让 Level-3 第一次覆盖了非幂等内核（训练步、原地更新、累加），这是超出论文的部分；代价是处理程序更长、需要 CTA 内线程束同步——这正是 §2 的时间片冲突与 DEF-38 的根源之一【推断】。

## 2. 安全边界：Trap 与上下文时间片（DEF-27 / DEF-40 / DEF-41）

### 2.1 现象（全部【实测】）

| 编号 | 场景 | 结果 |
|---|---|---|
| DEF-27 | HP 进程（Level-1）+ LP 进程（Level-3），GLB，无就绪门控 | 5060：每次运行约 1 次 Xid 109（约每 300 次挂起 1 次），两进程均收到 719，HP 请求停顿约 4.3 s；5080：未超时但 TPOT P99 3.1–3.5× |
| DEF-40 | 原生（非 XSched）进程与 Level-3 进程同卡 | 原生“受害者”2/2 次被杀死（719，受害者通道 Xid 109）；桌面进程 Xid 31（`MMU Fault … faulted @ 0x0`），一次桌面冻结 |
| DEF-41 | 两个同时运行 Level-3 的进程，无协调 | 14/14 次运行 Xid 109；主机级脉冲串行锁无效 |
| 外来负载实验 | S8 服务测试 + 同卡原生 GEMM，放行脉冲 | 1/4 次 Xid 109 并停顿 4.3 s；TTFT P99 约 25 ms（平常 8–11 ms） |
| 对照 | 同上，默认（检测到外来上下文不发脉冲） | 0 Xid，TTFT P99 13–14 ms |
| 对照 | 单进程内任意多条 Level-3 流（DEF-38 修复后） | 26/26 + 6/6 运行、约 11 万次挂起，0 Xid |

### 2.2 机理

**事实（代码）**：我们的 Cave 0 由驱动原有 Trap 处理程序在挂钩点调用；第一条判断检查陷入原因寄存器 `R2 & 0x11`，非零（硬件上下文切换 CILP / GfxP）就**原样交还驱动的处理程序**。也就是说，**计算上下文切换的保存过程本身也走 Trap 处理程序**【实测：代码与逆向记录】。

**由此推出（【推断】）**：

1. 一个线程束已经在执行处理程序（我们的代码）时，不会再接受新的陷入（硬件不嵌套 Trap；本项目在 DEF-38 中观察到“处理程序中的线程束错过脉冲”的后果）。上下文切换要保存它的状态，只能等它离开处理程序。
2. Mode 5 处理程序要整 CTA 同步（`BAR.SYNC.TRAP`）并保存大量状态。若切换请求在此期间到达，CTA 中已被切换机制陷入的线程束停在驱动的保存路径，仍在我们处理程序中的线程束停在 `BAR.SYNC.TRAP` 等它们——两边都无法前进，直到驱动的上下文切换超时 → **Xid 109**，驱动重置该通道，进程收到 719。现象中的“停顿约 4.3 s 后恢复”就是超时 + 恢复时间。
3. 非 XSched 上下文没有我们的处理程序：脉冲把它的线程束带进驱动原有处理程序，陷入原因不被识别 → 计算上下文挂住直到切换超时（Xid 109），图形上下文跳到地址 0（Xid 31）。

**不确定之处**：切换超时的确切阈值、硬件对“处理程序中的线程束”的处理细节未公开；上面第 2 条的“互相等待”是与全部现象一致的解释，没有直接观察到硬件内部状态【推断】。

### 2.3 与 DEF-38 的区别（为什么那种卡死是永久的）

DEF-38 发生在**同一进程**内（一个上下文、没有时间片切换）：队列 B 的脉冲恰在队列 A 的 cmd 写入落地时到达，A 的同一个 CTA 中一部分线程束读到旧值返回用户代码（停在用户 `BAR.SYNC`），另一部分读到新值停在 `BAR.SYNC.TRAP`。没有任何切换请求，也就没有超时机制介入，CTA 永远占着 SM（实测 15 分钟、GPU 100%、功耗 48 W）。恢复脉冲不能解开（实测 8 次无效；硬件原因未查明【推测：已在处理程序中的线程束不再陷入，用户态线程束停在屏障上】）。修复是预防：同一上下文内所有 Trap 操作串行（DEF-38 门控），门控开启后再无卡死【实测】。所以“Trap 之后再进入 Trap”不是卡死的直接原因；直接原因是**同一个 CTA 内线程束的决定不一致导致的双屏障死锁**（同进程）或**处理程序执行期间发生上下文切换**（跨进程）。

### 2.4 现在的处理（分层）

| 层 | 作用 | 覆盖 |
|---|---|---|
| 单进程 | 同一上下文内无时间片切换；DEF-38 门控串行所有 Trap 操作 | 任意多条 Level-3 流，安全【实测】 |
| 就绪门控（DEF-27，GLB 下默认） | HP 从空闲变就绪时，`xserver` 先挂起 LP、等驱逐完成，再放行 HP 的发射 | HP（Level-1）+ LP（Level-3）进程【实测：5060 0 Xid，5080 P99 1.10–1.29×】 |
| Level-3 轮换（DEF-41） | `xserver` 同一时刻只恢复一个进程的 Level-3 队列，20 ms 轮换；每个进程发布“已排空”字节，对端已排空才允许发脉冲 | 多个 Level-3 进程【实测：3/3 + 1/1，0 Xid，每 LP 约 900 次脉冲】 |
| 外来上下文检测（DEF-40） | 每次发脉冲前同步查询 GPU 进程列表（约 6 µs），有未登记进程就不发脉冲 | 其他用户 / 桌面 / 非 XSched 进程【实测：受害者 2/2 不受影响】 |
| 守护脚本 | 测试期间出现外来作业 1 s 内停止本测试 | 共享测试机 |

**残留（无法用软件完全消除）**：(a) 检查与 BAR0 写入之间的微秒级窗口：外来上下文恰在此时开始运行；(b) 不经 `xserver` 的多个 Level-3 进程：对端在检查后立即恢复的微秒级窗口；(c) 同一进程中没有 XQueue 的其他上下文（例如自建的第二个 `CUcontext`）不受保护。

### 2.5 能否靠调整 TSG / 时间片解决？

- **关闭时间片**：多个上下文都有工作时 GPU 必须在它们之间切换；GeForce 上没有“关闭时间片轮转”的选项【推断】。
- **加长时间片**（`nvidia-smi compute-policy` 一类设置，本机未验证是否支持 GeForce）：切换请求变少，冲突概率按比例下降，但**不能消除**——只要有一次切换落在处理程序执行期间，按 §2.2 的机理就会超时；同时损害其他租户的公平性与延迟【推断】。
- **独占进程模式**（`EXCLUSIVE_PROCESS`）：只允许一个上下文，冲突消失，但也失去多进程共享【推断】。
- **MPS**：多个客户端进程共用 MPS 服务器的一个上下文，从结构上去掉客户端之间的时间片切换，是最有希望的结构性方案；但处理程序要装在服务器的上下文中、控制块要按客户端区分，**本项目未实现、未验证**。
- **Context CILP 后端**（本项目已有，≈ 论文的 TSG 方式）：直接使用硬件上下文切换保存状态，不执行我们的处理程序代码，因此没有这类冲突；切换延迟约 420 µs（P99 476 µs）【实测】，支持非幂等；但粒度是整个进程（上下文），无法区分同一进程内的流。跨进程的 HP/LP 隔离可以考虑以它为主、Trap 引擎用于进程内细粒度抢占【建议，未做组合验证】。

### 2.6 论文是否有同样的问题

论文的队列方式与本项目是同一类机制（控制寄存器触发全 GPU 陷入 + 扩展处理程序），原理上同样受“处理程序执行期间发生上下文切换”影响；但论文的处理程序只识别并中止，不做 CTA 级同步与大量状态保存，窗口小得多，且论文的多进程实验未报告这类问题【推断：论文未讨论，无法确认其实际表现】。论文的 TSG 方式使用硬件上下文切换本身，不存在此问题。

### 2.7 结论：能否投入生产

- **可以**：专用 GPU（常见于推理集群：一块 GPU 分配给一组服务），所有使用 GPU 的进程都在 XSched 下，跨进程调度经 `xserver`。这正是本项目端到端验证的形态。
- **会自动退化为 Level-1**（安全但无中途抢占）：GPU 上有不受控的租户（共享开发机、Kubernetes 时间片共享未接入 XSched 的 Pod）、驱动显示器的 GPU（桌面图形上下文常驻）。
- **不建议**：关闭 DEF-40 检测（`XSCHED_SM120_FOREIGN_CTX=allow`）在共享 GPU 上运行——会杀死其他租户的作业【实测】。

## 3. 硬件限制：寄存器文件分配满时不接受 Trap（DEF-34）

**现象**【实测】：255 寄存器 × 128 线程 × 每 SM 2 个 CTA 的内核，1,600 多次挂起中没有一个 CTA 被驱逐。系统地改变配置：

| 每 SM 配置 | 已分配寄存器 / 65,536 | 驱逐次数 |
|---|---|---|
| 168 寄存器 × 128 线程 × 2 CTA | 43,008 | 41/52 |
| 240 × 2 CTA | 61,440 | 56/82 |
| 248 × 2 CTA | 63,488 | 57/81 |
| 168 × 3 CTA | 64,512（空闲 1,024） | 45/59 |
| 256（分配粒度）× 2 CTA | **65,536（空闲 0）** | **0/61** |
| 256 × 1 CTA | 32,768 | 46/60 |

**条件**：一个 SM 上驻留 CTA 的寄存器分配**正好用尽整个寄存器文件**（按 256 寄存器 / 线程束的分配粒度计算）。只要还有哪怕 1,024 个（4 个线程束粒度）空闲寄存器，就正常驱逐；与每线程寄存器数无关（同一内核每 SM 1 个 CTA 时正常）。

**表现**：脉冲不被这些 SM 接受，线程束不进入处理程序；挂起只能等内核自然结束（等价于 Level-1）。数据正确（108 次运行 0 错）【实测】。

**原因**【推测】：陷入处理需要每个 SM 有一定的空闲寄存器（处理程序的工作寄存器或硬件保存区），寄存器文件满时异常被延后。未找到公开资料证实。

**哪些内核会触发**：寄存器多、线程多、每 SM 恰好 1–2 个 CTA 填满寄存器文件的高度调优内核。典型：255 寄存器 × 256 线程 × 1 CTA（Marlin AWQ GEMM）、255 × 128 × 2、128 × 512 × 1。实测：Suite 7 的 49 个算子中 1 个（cutlass INT8 GEMM）；vLLM 7B-AWQ 中 **19% 的 Trap 托管内核**（Marlin GEMM、`_topk_topp_kernel`、`_penalties_kernel`），3B BF16 中没有。

**对通用性的影响**：HP 尾延迟受这些内核的长度限制（7B-AWQ 的 HP P99 30.8–36.1 ms，3B 为 30.3–31.8 ms）；对 decode 阶段的短内核影响小，对长的 RF 满内核（大 prefill GEMM 若采用此类配置）会使最坏延迟回到 Level-1 水平。现已按几何形状检测并计数（`rf_full`），可选显式路由到 Level-1。软件上的缓解只有“降低占用率”（每 SM 少一个线程束），对“单 CTA 就填满”的内核无效。

## 4. 退化为 Level-1 的内核类别

| 类别 | 为什么不能 Trap 抢占 | 当前处理 | 当前栈中的出现情况【实测】 | 趋势 |
|---|---|---|---|---|
| 协作启动（`grid.sync`） | 网格内所有 CTA 必须同时驻留；部分驱逐后剩余 CTA 在网格屏障上等不到 | Level-1 边界 | Suite 7、vLLM：0 | 少数算法（全局同步的规约 / 求解器）使用 |
| 线程块 Cluster + DSMEM（DEF-19） | Cluster 屏障相位、DSMEM 映射不在 Trap 帧中；单波实验模式 5080 上偶发 1–2 个 CTA 错误 | Level-1 边界 | 0 | sm_90+ 的高性能 GEMM / 注意力内核会用 |
| 硬件 mbarrier（`SYNCS`，TMA 流水线） | mbarrier 是带硬件语义的共享内存对象（事务计数、相位），无法保存后在另一次发射中重建 | Level-1 边界 | 0 | **最大的未来缺口**：CUTLASS 3.x、FlashAttention-3/4 等基于 TMA + warp 专用化的内核普遍使用 |
| 不可展平的 CUDA Graph | 整图在驱动内部发射，无法逐内核插桩；且图内核在发射时继承函数的参数窗口（DEF-32） | 默认展平为逐内核提交（DEF-09）；含主机节点、条件节点、`extra` 参数等的图保持整图 → Level-1 边界 | vLLM 7B：155/155 图展平 | 展平 CPU 代价：0.5B decode 吞吐 −36%，7B −20%，prefill −10–16%（OBS-17） |
| 寄存器文件满（DEF-34） | 见 §3 | 统计；可选 Level-1 | vLLM 7B-AWQ 19% | 视库的调优策略 |
| 插桩失败 | 二进制无法安全改写 | Level-1 边界 | 0 | — |
| 短 CTA 路由（性能策略） | 无循环、短 CTA、实测 ≤ 200 µs：Level-1 延迟本来就短，省掉 Guardian 成本 | 主动路由到 Level-1 | vLLM 3B 2.3%，7B 2.3% | — |

论文对应的立场：论文的 Lv3 只覆盖人工标注的幂等内核，其余内核本来就只有 Lv1/Lv2；论文把 CUDA Graph 列为“单命令任务”的局限。Cluster、mbarrier、TMA 是论文实验平台（Volta / Ampere）之后的特性，论文未涉及。

**对实际生产的影响**【推断】：在当前 PyTorch / vLLM 的 sm_120 软件栈上，上述特性几乎不出现，Level-3 覆盖率高（Suite 7：148/148 次调用 Trap 托管；vLLM 3B：97.7%）。但新一代内核库向 TMA + mbarrier + Cluster 迁移是明确的方向；对这类内核，本机制只能在内核边界挂起，其最坏延迟等于内核长度。要真正覆盖它们，需要能保存 / 重建 mbarrier 与 Cluster 状态的硬件或驱动支持，或改走上下文级抢占（Context CILP）。

## 8. 工程与部署层面的约束

- **依赖未公开的驱动内部结构**：Trap 处理程序布局、挂钩点、内部导出表、BAR0 STOP_TRIGGER 寄存器都来自逆向；驱动升级可能改变布局。已做的防护：安装前校验指纹与挂钩点指令，不认识时整体退化为 Level-1（第一梯队 4，`SYN-no-engine`）。没有厂商支持时，这是长期维护风险。
- **权限**：BAR0 写入需要 root，或部署 `xsched-bar0d` 代理（root 启动、只提供脉冲操作）。在多租户环境中这是需要安全评审的特权组件。
- **显存**：Mode 5 为每个可能被驱逐的 CTA 预留保存区（寄存器、共享内存、局部内存），大网格 / 高占用内核的 arena 可达数百 MB；空闲时回收（MEM-1）。
- **可观测性**：路由统计、脉冲计数、恢复脉冲计数、停滞看门狗（`XSCHED_SM120_WATCHDOG_MS`）已具备；Xid 只能从内核日志获得。

## 9. 场景对照与预期

| 场景 | Level-3 的状态 | 预期 |
|---|---|---|
| 单进程内 HP / LP 多流（训练 + 推理同进程、服务框架内部优先级） | 安全，覆盖最完整 | HP 延迟与 LP 内核时长无关；最适合的场景 |
| 专用 GPU 上的多进程推理服务（HP Level-1 + LP Level-3，`xserver`） | 安全（就绪门控） | 已验证：HP ≈ 独占，LP 88–93% |
| 多个 LP 租户（多个 Level-3 进程） | 安全（轮换） | LP 之间不再并发，按 20 ms 轮换；总吞吐近似原先的时间片共享 |
| 共享 GPU / 不受控租户 | 自动退化 Level-1 | 不伤害其他租户；HP 尾延迟回到 Level-1 水平 |
| 驱动显示器的 GPU | 自动退化 Level-1 | 显式放行会打到桌面程序（实测） |
| LP 为长 CTA / 持久化内核且占满 SM | Level-3 价值最大 | native 与 Level-1 的 HP 延迟随 LP 内核线性增长，Level-3 有界 |
| LP 为 RF 满内核（DEF-34） | 该内核退化 | 最坏延迟 = 内核长度 |
| LP 使用 TMA / mbarrier / Cluster 内核 | 退化 | 新一代内核库普及后覆盖率下降 |
| 小模型 decode + CUDA Graph | 可抢占但 CPU 成本高 | 展平使吞吐下降 20–36%；可按时长只展平长图 |
| 高频抢占 + 极大网格的逐元素内核 | 有饥饿防护 | 吞吐显著下降；此类工作负载更适合 Level-1 或较低抢占频率 |

**客观预期**：本项目证明了在消费级 Blackwell 上，无需修改应用和驱动，就能对非幂等内核做中途抢占并原位恢复，并在端到端推理服务中取得独占级的 HP 延迟。它的可用前提是“GPU 上的所有工作都在 XSched 的协调之下”；这一前提在专用推理 GPU 上可以满足，在共享或桌面 GPU 上不满足，届时系统安全地退化为 Level-1。要把它变成通用的生产组件，还缺三样东西：(1) 消除跨上下文冲突的结构性方案（MPS 单上下文或与 Context CILP 的组合，需要验证）；(2) 对 mbarrier / Cluster 状态的保存能力（取决于硬件 / 驱动）；(3) 不依赖逆向的稳定接口（需要厂商支持）。
