## 1. 起点与方法

### 1.1 起点

`v2.2.1` 在 Phase 1–2 中通过了自写微基准、11 项端到端用例、15 项库 / 硬件特性用例和 11 项真实 PyTorch 模型用例。Phase 3 的目标是把它放到**真实生产负载**上：主流 PyTorch 算子逐调用比特级核对、真实模型训练 / 推理、真实服务共置，并量化性能。

### 1.2 测试体系（本阶段建成）

| 套件 | 内容 | 判定方式 |

| 合成（`SYN`） | `test_partial_exit_p3`（部分退出 / 发散线程束）、`test_convbar_p3`（收敛屏障嵌套深度 D1–D6、寄存器压力 R0–R3、多波压测 `GRID_MULT=8`、12 内核链）、`test_percall_p3`（每调用开销）、`SYN-xq-idle` | 每次抢占后与不抢占结果逐元素比较 |

## 2. Phase 3.0：生产负载测试与 DEF-20

### 2.1 现象

Suite 7 在 Lv3 下：5080 24/29、5060 23/29 个算子通过。失败分三类——dtype 转换核恢复即 `cuda error 700/717`（两卡 100% 复现，DEF-14）；CUB Onesweep 排序、整型 `cumsum`、`topk`、`index_add_int32` 崩溃（DEF-15）；Triton 融合 RMSNorm **不报错但输出错误**，5 轮仅 1–2 轮正确（DEF-16）。另外长期存在的 `LIB-08` 15–38% 偶发 700、`LLM-07 m5` 约 1/3 偶发 700。

### 2.2 排查过程（假设 → 实验 → 结论）

1. 单独运行 `torch.sort` 不抢占全部通过 → **问题需要抢占**。
2. `CUDA_LAUNCH_BLOCKING=1` 下通过 → **与时序有关**。
3. 恢复遥测：所有失败都伴随 `evicted>0`，即执行中被驱逐（State B）。
4. 假设“在途命令（memset）在驱逐与恢复之间执行” → 遥测显示活跃内核之后没有在途命令 → **否定**。
5. 发现 5 个“崩溃算子”中 4 个其实是**校验代码自己**的 bool→int64 转换核被驱逐（T-1）→ 修正校验方法；最小复现：`x.to(int64)` 必崩，`x+1.0` 不崩。
6. 假设代码搬移（插桩后原内核移到 `+0x500`）破坏了相对跳转 → 无 `BRX/JMX`，`CALL.ABS` 用 `LEPC` 计算返回地址 → **否定**（但发现 DEF-22：`CALL.ABS` 未被识别为调用）。
7. 假设收敛屏障 `BMOV B0–B15` 手写编码错误 → `nvdisasm` 核对 32 条全对 → **否定**。
8. 假设 HP 干扰 → 无 HP 同样崩溃 → **否定**。
9. 假设部分退出 / 发散线程束 → `test_partial_exit_p3` 全过 → **否定**。
10. 假设在途加载 → 通过的 bf16 内核同样在等待 `LDG` 时被 Trap → **否定**。
11. 假设 SMEM 记账错误 → 实测 `%total_smem_size = SR_SMEMSZ − c[0][0x16c]`，用户 SMEM 从 `0x400` 开始，引擎拷贝长度正确 → **否定**（得到新知识，记为 OBS-8）。
12. 假设高编号收敛屏障（Trap 现场在 `BREAK.RELIABLE B6`）→ D1–D6 嵌套深度扫描全过，但 C1 失败 → 否定屏障编号，注意到 C1 用 15 个寄存器。
13. **寄存器压力扫描**：≤13 寄存器的合成内核永远通过，≥14 都会失败（单次抢占即可触发，错误线程在 lane / warp 间均匀分布，55 寄存器时 364 个线程束全错）→ 指向保存 `R14+` 的 Cave 2/5 级联。
14. **`SR_REGALLOC` 探针**：把内核二进制中的 `S2R SR_TID.X` 改写为 `S2R SR_REGALLOC`，读出值严格等于寄存器数（16/20/25/45/69/125/206），不是原设计假设的“+2/+3” → **根因确认**。
15. 把 `−3` 改为 `−1`：偶数寄存器内核全过，奇数仍失败 → 发现寄存器对越界 → 插桩时寄存器数向上取偶 → 全部合成用例通过。
16. 真实算子：两卡两构建 29/29；`LIB-08` 60/60、`LLM-07` 10/10。

### 2.3 一起提交的上一会话修复

- DEF-11：shim 漏拦截 `cuMemcpyAsync` / `cuMemAllocFromPoolAsync`（cuDNN LSTM 竞态）。
- DEF-12：恢复途中被再次抢占时保留 `active_kernel_idx` / `is_restore_wave`（条件清零）。
- DEF-13：cuDNN 多个内部流复用同一 `CUevent`，等待快照丢失 → 对非 XQueue 记录的事件同步等待；XQueue 排空后做硬件级 `StreamSynchronize/StreamQuery`。

### 2.4 这一阶段的其他发现

- **OBS-1**：5080 上 `linear_bwd_accum` / `batchnorm_train` 不同进程的整条作业摘要不同，但同进程 A/B 40/60 次逐次比特一致——是 cuBLAS / cuDNN 的进程级算法选择差异，不是数据损坏（T-10）。
- **OBS-3**：原生高优先级流（无调度器）在单算子微基准中 HP 延迟优于 Lv3（P50 0.11 vs 0.33 ms），因为短 CTA 内核可被硬件按 CTA 粒度插队。论文评测需加入该基线。
- **OBS-5**：PyTorch 2.11 在 RTX 50 上 29 个主流算子 100% 可被 Lv3 插桩，无 mbarrier / Cluster / Cooperative。

## 3. Phase 3.2：正确性收尾

### 3.1 DEF-21：恢复途中再次抢占

DEF-20 修复后：`DNN-06 torch.compile` 与真实服务在 HEAD 的恢复逻辑下出错（丢 CTA），而工作区的 DEF-12 逻辑通过；但合成 C1 两次抢占反而在 DEF-12 逻辑下 0/10。仔细检查合成测试：它用同步 `cudaMemcpy`（可分页内存）上传输入后，在非阻塞流上启动内核，两者没有顺序保证，网格尾部 CTA 读到旧输入（T-11）。补设备同步后 C1 通过。DEF-12 逻辑经约 3,000 次压测抢占验证，DEF-21 关闭。DEF-18（“DEF-12 改动使 LIB-08 失败率升高”）的结论也随之修订：那是与 DEF-20 叠加所致。

### 3.2 DEF-19：Cluster + DSMEM

`HW-06`（2×1×1 Cluster + 分布式共享内存）在 5080 上 10–40% 的运行中 1–2 个 CTA 结果错。Cluster 屏障相位与 DSMEM 映射不在 Trap 帧里，无法保存 / 重建。缓解：Cluster 内核默认走 Level-1。完整方案（未实现）：Guardian 用 `barrier.cluster` + DSMEM 广播 rank 0 的决定，让整个 Cluster 一致地排空或运行，不驱逐已运行的 Cluster。

### 3.3 DEF-22 / DEF-23

- DEF-22：调用检测漏了 `CALL.ABS.NOINC`（`0x343`），含此类调用的内核栈帧不会被保存（未触发，SASS 审查发现）。
- DEF-23：含调用内核的 LMEM 保存区固定按 4 KiB/线程预留，LayerNorm 在 5060 上要 231 MiB → 改为静态局部 + `CU_LIMIT_STACK_SIZE`。

## 4. Phase 3.3：性能

### 4.1 DEF-17：Entry Guardian 开销——一步步拆解

1. **定位**：对照实验显示开销与 CTA 长度成反比（短 CTA 访存算子最高，5080 `rope_apply` +101%）。
2. **三个版本**：原版（v1）；默认版（去掉 slot 28 的冗余 `cmd` 重读，依据“写入先于脉冲”的顺序论证）；实验 v2（异步发出访存）。默认版把 5080 `embedding` +22.8% → +1.9%、`gelu` +18.3% → +0.3%。
3. **v2 为什么不能用（EXP-1）**：`LLM-08`（两条 Lv3 队列 + HP 流）在 5080 上 v2 11/61 次出错、串行版本 0/78。用子开关 `_SERIAL_HDR` / `_SERIAL_SREG` 二分，仍未完全定位。推测 Trap 送达时 Guardian 发出的访存尚未完成。保留为实验开关。
4. **短 CTA 路由**：对“每个线程每条指令至多执行一次”的内核（无回边、无调用），Level-1 边界的抢占延迟就是该内核自身的短时长，却能省掉每个 CTA 的 Guardian。用 3,653 条分支拟合确认 `BRA` 偏移编码后实现 loop-free 判定。`transpose_copy` / `rope_apply` 降到 < 3%。代价：被路由内核的 HP 延迟上限 = 其自身时长。
5. **`BAR.RED` norm_gate**：屏障后读 `entry_dec` 是一次串行全局访存。用 `BAR.RED.OR` 在屏障时归约“是否有线程登记了排空”，只在可能排空时读取。需要新的 SASS 编码（`BAR.RED.OR`、`B2R.RESULT`、带谓词源的 `ISETP`），反汇编核对后实现；`restore_path` / `replay_state_c` 后移一槽，Cave 0 改为使用运行时锚点。5060 `sort` +13% → +7%。
6. **门控镜像**：5080 上剩余成本集中在 `sort` / `topk`。测量探针把 Guardian 的两次控制头读取换成常数（会使抢占失效，仅用于测量），5080 纯 Mode 5 `rope_apply` +54% → +5%、`topk` +10% → +4%——说明成本是数千 CTA 同读一条缓存行的 L2 热点。改为每 SM 一行镜像（`SR_VIRTUALSMID` 选行）。
   - 尝试过的探针：先试用 `LD.E.CONSTANT` / 弱序 `LD.E` 让读取走 L1 → 运行时非法指令 715，放弃（新知识：这两种通用地址形式在 sm_120 上不可用）。
   - **开发中的缺陷 T-21**：第一版 `PreemptStream()` 用读到的 `is_restore_wave` 同时写镜像两个字段。多波压测 4/4 次非法指令，镜像关闭 4/4 通过。写一致性检查器（`XSCHED_SM120_GATE_MIRROR_CHECK`）后看到“镜像 {5,1} vs 控制头 {5,0}”：读取之后条件清零内核已把控制头的 `is_restore_wave` 清 0，镜像留下了过期的 1。改为只写 `cmd`，并确立“镜像严格跟随控制头写入者”的规则。
   - 结果：5080 `sort` +14.8% → +3.3%、`rope`（纯 Mode 5）+54% → +7%。

### 4.2 PERF-1：每调用开销

C++ 微基准（`test_percall_p3`）显示每次调用 Lv1 8–17 µs。原因是每条命令都交给发射线程（futex 唤醒）且同步也要排队等发射线程。改为直接提交（自适应：发射线程休眠，或上一次调用只有 1 条命令）+ 调用方 `WaitAll` + 有界自旋 + 布局缓存。单内核调用 Lv1 +1.1–1.2 µs、Lv3 +2.2–2.4 µs（两卡）。

过程中的误判：自写微基准一度显示“Lv3 下循环内核出错”，实际是测试内核写 `out[1024+b]` 而缓冲区只有 4 KiB，越界写落到相邻的 XSched 控制内存（T-16，OBS-13：用户内核的越界写可以破坏 XSched 的设备端结构）；“Lv3 下事件计时每次多 2.4 ms”实际是首次发射的插桩时间（约 19 ms）被计入平均（T-17）。

### 4.3 PERF-2：透传发射

Suite 8 中，`request` 策略在 HP 请求期间已经完全挂起 LP，5080 上 HP TPOT 仍为无 XSched 时的 1.23×；同一进程中 LP 线程启动之前测得的 solo TPOT 也慢同样幅度——说明代价与调度无关，来自“加载了 XSched”本身。`perf` 采样定位到 `cuXtraKernelGetFunction`（8.4% 样本）与每次透传都清零参数窗口。单内核微基准看不出来，因为驱动对同一句柄的转换有缓存（T-20）。修复后 TPOT 1.01–1.06×。

### 4.4 MEM-1 与 DEF-24

- MEM-1：arena 增长后旧 arena 永不释放 → 在同步点按规则回收（原理 §6.3）。
- DEF-24：调用检测还漏了间接调用 `CALL.REL.NOINC Rx`（`0x344`）与 `RET`（`0x950`）。

### 4.5 调度目标的分析

目标“原负载下 LP > 80% 且 TPOT 不劣化”。推导出时间共享的上限 `LP ≤ 1 − 占空比`（原负载 62–74%），Lv1 已接近上限。尝试四种策略（`request / prefill / token / slo`），在较低负载（1.5 s / 3 s 间隔）下 `request` 两卡 LP 79–95%、TPOT 1.00×。尝试用 CUDA green context 做空间共享突破上限：先验证 green context 流能被 PyTorch 用作 `ExternalStream`、4096² GEMM 在 8/16/24 SM 上分别慢 3.66/1.82/1.24×（理论 3.75/1.88/1.25）、SM 数有分配粒度（5060 上请求 20–24 都得到 24）；共置结果 5060 P99 +44%、5080 P50 +27–43%。为排除 GIL，把 `sys.setswitchinterval` 从 5 ms 调到 0.2–0.5 ms，P99 不变。结论：两类机制在原负载下都不可达。

### 4.6 测试方法上的修正

- T-18：生产路由会把机制测试的被测内核移出 Mode 5 → 机制套件关闭路由运行，Suite 7 增加纯 Mode 5 列。
- T-19：`LIB-06` 的 LP 只有一次 cuFFT（< 1 ms），测试在 800 µs 后才抢占；提交路径加速后 LP 先结束，`preempts=0` 判失败。最初误归因于路由（T-18），关闭路由后仍失败才找到真因。改为 4 次原地 FFT + 按位比较，并给该文件 23 处可分页 H2D 拷贝补设备同步（T-11 同类）。

## 5. Phase 3.4-1：DEF-10 非 root

先以普通用户直接运行 Lv3 测试：Trap 补丁、Guardian、控制内存全部正常，只有脉冲失败，系统退化为“等内核跑完”（挂起 9–16 ms，结果仍正确）。于是 DEF-10 的范围被精确限定为“一个寄存器的一次写序列”，设计成只能发脉冲的特权代理。验证包括：两卡非root 全套（37/37、50/50）、协议畸形请求、无权限、限流、伪造的“服务另一块 GPU”的代理、路径超长、运行中杀掉并重启代理（同进程内自动重连，1,980 次 → 中断期间 1,089 次退化 → 4,131 次）。开销用同会话交替 A/B 测得 +2–15 µs；跨运行比较的 +22–27 µs 被证明是运行间波动。

## 6. Phase 3.4-2：多进程

### 6.1 测试设计

`bench_mp_serving_p34.py`：编排进程依次启动 LP 进程（先测金标准与独占吞吐，避免两个进程同时加载模型干扰测量）与 HP 进程；两者通过抽象命名空间 Unix socket 协调测量窗口。6 种模式：`solo`、`native`、`req-lv1/lv3`（HP 请求前让 LP 进程挂起并**等确认**）、`glb-lv1/lv3`（XSched 全局调度器，完全透明）。

### 6.2 OBS-7 证实

`req-*` TPOT 1.00×（单进程 1.02–1.07×）。附带观察：5060 上 `solo` 模式（请求之间 GPU 空闲 0.5 s）的 TPOT 比背靠背测得的金标准高 18%——GPU 在空闲间隙降频；共置时 LP 让 GPU 保持高频，HP 反而更快。5080 无此现象。

### 6.3 DEF-25：一次误判（已撤回）

为了让全局调度器正确工作，先检查“同步后队列是否变为 Idle”：同步返回后**立即**查询，Level-1 200/200 次仍为 Ready。于是判定“调用方 `WaitAll` 快速路径漏报 Idle，调度器会认为队列永远忙”，并让调用线程在同步成功后直接置 Idle。这个“修复”使全量回归中 `HW-05`（空闲队列挂起 / 恢复）两卡断言失败：`last_enqueued_cmd_ must be an XQueueWaitAllCommand if the XQueue is idle`。重新阅读命令缓冲区：发射线程在排空后会自己生成后台同步与 `WaitAll` 并完成转换；Idle 状态有一个约定——最后入队的命令必是已完成的 `WaitAll`，`EnqueueXQueueWaitAllCommand()` 依赖它在 Idle 时直接返回。改为轮询测量：不做任何改动时，同步返回后约 21 µs（最大 41 µs）队列即 Idle。改动全部回退（`HW-05` 3/3 通过）。同轮 5080 `S8-ppl-lv3-prefill` 出现的 1 次 LP 不一致，在回退后两卡各重复 12 次（约 6,900 次迭代）0 次出现，与“由该改动引起”相符，但单次事件不足以证明。

教训（T-22）：状态类测试先区分“立即”与“最终”语义、测清异步转换耗时；任何绕开既有组件改状态的修复，先找出该状态的全部读者及其约定。

### 6.4 DEF-26：调度器线程无上下文

首轮 `glb-lv3` 的 LP 进程断言失败 `sm120 PrepareLaunch failed`，随后 `Resource deadlock avoided`。Level-1 不受影响而 Level-3 出错 → 区别在恢复路径：Level-3 的 `Reactivate()` 要发射内核，而调度器执行线程从未设置 CUDA 上下文。修复后断言消失。

### 6.5 DEF-27：从“LP 13%”到 Xid 109

修复 DEF-26 后，`glb-lv3` 不再断言，但单次运行 141 s（正常 19 s）、LP 13%，且 TPOT / TTFT 统计看起来正常。加入 `.item()` 计时与每请求端到端时间后发现：个别请求整体被阻塞约 4.3 s，同时两个进程在**同一微秒**报 `cuda error 719`。两个独立上下文同时出错指向 GPU 级事件，于是查内核日志：`NVRM: Xid 109, CTX SWITCH TIMEOUT`，4 次全部来自 `glb-lv3` 运行，`req-lv3` 与其他模式 0 次。对比两种模式的唯一区别——HP 是否等 LP 驱逐确认后才发射——得出机制（原理 §9.4）。当时先做缓解（GLB 下走 Level-1），记录为开放。

### 6.6 DEF-28：残留 IPC 队列导致挂起

全量回归以 root 跑了新加的 Suite 9 之后，再以普通用户运行 `glb-*` 两次都超时（600 / 900 s）。把 `xserver` 输出从 `/dev/null` 改为日志后看到 `MessageQueue CPPIPC-1 (key: 0x1) already exists, deleting ... Operation not permitted`。消息队列不在 `/dev/shm`，是 SysV 队列：`ipcs -q` 显示一个 root 所有、含 439 条未读消息的键 `0x1` 队列。`xserver` 只处理 SIGINT / SIGQUIT，测试脚本用 `terminate()`（SIGTERM）结束它。修复见原理 §9.5。

### 6.7 OBS-14：桌面图形进程的 Xid 31

整理内核日志时看到 `gnome-shell` / `ghostty` 的 Xid 31（MMU 故障，地址 0）。逐条与测试日志对时间：00:31:23 的事件发生在 00:31:22 开始的多波压测启动后 1 s；06:15:39 的事件发生在代理重启压测期间；11-25 20:14 的事件早于本会话日志，无法对应。后来在门控测试中又出现 `Xwayland`、`gnome-shell` 各一次。进程 pid 均未变，即都已恢复。

### 6.8 一次中断：主机重启

11-26 09:14 本地主机正常重启（`systemd-reboot.service` 有序关机，非崩溃，此前最后一个 Xid 在 07:07），`/tmp` 中的构建、安装、测试二进制、环境文件与文档工具全部丢失。依据仓库与会话记录重建（构建命令、环境文件、低负载计划从 5080 的副本还原、`sanitize.py` 从会话记录还原）。不能进仓库的工具（脱敏脚本含他人用户名）另存私有目录 `~/.xsched_p3_tools`。

## 7. DEF-27 根本修复：就绪门控

### 7.1 方案选择

| 方案 | 评估 |
|---|---|
| 通过 RM 控制把 LP 上下文的计算抢占模式设为 CTA / WFI，或加长其时间片 | 代码已有 RM 调用（`NV2080_CTRL_CMD_GR_SET_CTXSW_PREEMPTION_MODE`、`NVA06C_CTRL_CMD_SET_TIMESLICE`），但 RM 句柄靠 `ioctl` 符号插桩捕获，在 Python 进程里 libc 的 `ioctl` 先于 XSched 解析，需要 `LD_PRELOAD`；且加长时间片只降低概率不消除竞争 |
| 全局调度协议增加“低优先级驱逐完成”确认，HP 收到后才发射 | 纯软件，确定性地消除竞争（与 `req-lv3` 相同的保证）；已有 `OperationCompleteEvent` 与 `WaitOperations` 基础设施 → **采用** |

### 7.2 实现与验证

实现见原理 §9.4。验证按风险分级：先在 5060 上只用 Level-1 测门控本身（无 Trap、无重置风险）：0 次超时；1 µs 超时探针 + 统计行确认门控真的在等待（HP 每次 15–31 µs）。再在无显示的 5080 上做真正的 Lv3：无门控 3 次（0 次 Xid，但 P99 3.1–3.5×，19–22 ms 卡顿）、有门控 10 次（P99 1.10–1.29×，0 次 Xid）。最后在曾 4/4 复现 Xid 109 的 5060 上有门控 6 次：0 次 Xid 109（其间 1 次 `Xwayland` Xid 31 属于 OBS-14）。

### 7.3 Level-1 尾延迟的排查（一次被噪声误导又纠正的过程）

门控默认开启后，5060 回归中 `glb-lv1` 的 P99 为 1.79×，早先某次门控运行中也出现 21 ms。四步排查：

1. **假设：服务端也在等待 Level-1 挂起**（Level-1 挂起可能要等 LP 正在执行的内核）。改为只等待 Level-3 挂起 → 仍有 2/4 次长尾 → 不是主因（但这一改动本身合理，保留）。
2. **门控统计**：最坏一次运行中 HP 门控等待最大只有 48 µs → 长尾不在门控等待，而在 GPU 上被 LP 工作拖慢。
3. **假设：发射线程在日志满时不检查暂停（OBS-15），挂起的 LP 漏出命令**。修正后交替 A/B（8×8）：修正反而略差（P99 > 14 ms 的运行 6/8 vs 3/8，P50 1.010× vs 0.987×）；`request` 策略 6×6 无差别 → 修正无收益，回退，记为观察。
4. **门控开 / 关交替 A/B（8×8）**：P50 0.968× / 0.969×，P99 1.28–2.32× / 1.23–2.40×，P99 > 14 ms 各 4/8 → 门控对 Level-1 无影响；早先“门控前 10 次都 ≤ 12 ms”的对比是抽样所致。

教训：P99 由约 300 步中的 3 步决定，单次运行之间波动可达 2 倍；判断此类差异必须用交替（interleaved）A/B 和足够样本，并先用直接测量（门控统计）排除假设。

### 7.4 共享主机上的测试安全（T-24）

5080 回归开始时，另一用户在运行他自己的 XSched `xserver`（同一 SysV 键 `0x1`、同一端口）和 GPU 作业。我们的 Suite 9 若以 root 启动 `xserver`，会删除对方的队列——root 有权限。在任何本方测试运行之前发现并只停止了本方的等待进程（按 PID，未使用宽泛的 `pkill`）。之后：测试脚本只要键 `0x1` 队列属于他人就拒绝启动（包括 root）；回归在 GPU 与 IPC 都空闲后才开始；证据中 GPU 占用记录（含他人进程路径）一律脱敏，并复查了已提交证据（无泄露）。

同一轮 5080 回归中 4 项在 CUDA 初始化阶段报 `CUDA unknown error`（含一项 native），同时段内核日志有 7 条 `NVRM: Going over RM unhandled interrupt threshold`。逐条对照时间：全部发生在本方回归处于“等待 GPU 空闲”、没有任何本方测试运行的时刻 → 归因于他人负载；GPU 空闲后复跑通过。

## 7b. Phase 3.5 第一梯队的探索过程（2026-11-26）

结果见 [`SM120_V2_PHASE3_5_TIER1_ZH.md`](SM120_V2_PHASE3_5_TIER1_ZH.md)。这一段记录“怎么走到那里”。

1. **价值实验先否定了一个直觉**。原以为 native 高优先级流会被长 LP 内核拖住，结果 cuBLAS GEMM / SDPA 下 native 的 HP P99 只有 1 ms 左右：GPU 会把 HP 的 CTA 放进 LP 留下的空位（OBS-16）。于是加了“占满 SM”的持久化 GEMM（BK=64、3 级流水，约 96 KB 共享内存），native 才表现出随 LP 内核线性增长的尾延迟——价值边界由此明确。
2. **5060 的 Lv3 尾延迟**：最初怀疑“上一次恢复尚未完成”，加大 HP 间隔 20 ms 无变化而否定；关闭短 CTA 路由后消失，定位到被路由的毫秒级校验内核（DEF-30）。修复后的第一版又“好得可疑”——路由统计里 `lv1_short_cta` 为 0，查出计时探针查询了尚未 record 的事件（T-25）。
3. **图展平**按“实例化时记录、发射时提交”实现。PyTorch 的整网捕获测试一开始与原生结果不一致，原因在测试：没有按 PyTorch 文档在捕获前 `zero_grad(set_to_none=True)`，梯度在重放间累加；改正后比特一致。
4. **vLLM 的 22% 开销**：调阈值、自旋、直接提交都无效，说明不是交接开销；cProfile 对比 native 与 Level-1 的同一函数表，差异集中在 `Event.wait`，追到 `copy_stream.wait_stream()` → 跨流等待阻塞调用线程（DEF-29）。
5. **主机标志桥的死锁**：合成测试全过、vLLM 卡在启动。`gdb` 三个线程的栈拼出环：模块加载持锁等 GPU 空闲、GPU 等标志、标志等发射、发射等锁。换成“提升等待流为 XQueue”后无环。
6. **一个“回归”其实是测试竞态**（T-26）：新路径在回归里 30/30 损坏，手工 3 次通过 1 次失败；把旧阻塞路径也跑出 30/30 损坏后，才意识到问题与新代码无关，打印 native 确定性后定位为输入生成与非阻塞流的竞争。
7. **7B 吞吐各模式完全相同、挂起 ≈ 0**：不是“XQueue 没开销”，而是 vLLM 在另一个流上运行（OBS-18）；用诊断脚本对比 `main_stream` 与 XQueue 流确认。
8. **DEF-32**：DEF-29 修复后不展平的 vLLM 每次抢占后都出错。先按代码审查修了 DEF-31（重发非 killable 命令），无效；又假设“捕获时固化了过期窗口”，在捕获开始时清零，仍无效——两个假设都被 A/B 否定。`XSCHED_SM120_TRACE_LAUNCH` 的恢复日志给出决定性线索：`active_idx=4231` 不在日志里、排空 35,832 个 CTA。结论是图节点在**发射时**读取函数当前的参数窗口；在整图发射前于 `LaunchMutex` 内清零后 32/32。合成复现用例三种写法都未能触发，说明真实框架的发射序列比手写用例复杂——最终以 vLLM 本身作为验证。
9. **收尾回归**：5080 的 LIB-12 退出时堆损坏。关闭新功能、换提交版本的库、再换提交版本的测试程序，都仍失败，排除了“本阶段引入”；`gdb` 定位到静态析构里的 Trap 处理程序恢复（DEF-33）。5060 上另有 3 次“进程刚启动就出错”（OBS-20），受控复现 54 次未出现，作为开放项保留。

| T-26 | PyTorch 流池中的流是 non-blocking 的；默认流上生成的输入先同步再在其他流上使用；测试报告 native 确定性 |

| — | 查“新代码引入的回归”时，先用提交版本的库与测试程序复测，排除环境与潜在缺陷 |
| — | P99 类指标用交替 A/B 与足够样本判断；跨运行比较只能作为线索 |
| — | 每个结论两卡复现；每次改动两卡全量回归后才合入；所有数字落盘为脱敏证据 |
