## 1. DEF-21：恢复波次中再抢占

### 1.1 重新审视证据
- 失败在进程内“全有或全无”（同一进程 10 轮全错或全对），且**零抢占的轮次也会失败**，错误线程总是网格尾部连续的一段 CTA（CTA 16–20 … 59），这些 CTA 确实执行了但读到旧输入。
- 原因是合成测试的初始化：每轮用同步 `cudaMemcpy` 从**可分页**主机内存上传输入，再在**非阻塞流**上启动内核。CUDA 文档允许这种拷贝在数据真正到达设备前返回，非阻塞流也不会与之排序，于是内核可能读到上传未完成的尾部。
- 修正：所有上传改为 `H2D()`（拷贝后 `cudaDeviceSynchronize()`）。修正后：12 进程 × np∈{0,2,3} 共 36 个进程 **0 失败**；12 内核顺序 3 次抢占 3/3 轮全过。
- 结论：上一轮“工作区 DEF-12 逻辑在 5060 上 C1 两次抢占 0/10、HEAD 逻辑 10/10”的对比，实际上是**每种构建各 1 个进程**的样本（失败按进程整体出现），不构成证据。

### 1.2 专项压测（工作区 DEF-12 逻辑）
`test_convbar_p3.cu` 新增开关：`GRID_MULT`（每 SM 的 CTA 数，8 = 多波次）、`CHAIN`（每轮排队的内核数）、`GAP_US`（抢占间隔）、`TARGET_MS`（单内核时长）。

| 配置（RTX 5060，12 个合成内核 × 3 轮） | 每轮抢占 | 结果 | 覆盖 |
|---|---:|---|---|
| grid∈{2,8} × chain∈{1,4} × gap∈{300,1500 µs} | 8 | **96/96 通过**（约 2,300 次抢占） | R3/grid8/chain4/gap300：24 次中 21 次命中恢复波次（含 State-B 驱逐与 State-C 排空） |
| grid∈{2,8}，chain=6，gap=1 ms，每内核 4 ms | 10 | **24/24 通过**（720 次抢占） | 178/360、240/360 次命中恢复波次；抢占落在 147 / 120 个不同内核位置（跨内核边界） |

5080 上同样的合成与压测用例纳入全量回归（§6）。

## 2. DEF-19 / DEF-22 / DEF-23

- **DEF-19**：`CudaQueueLv3Trap::OnHwCommandSubmit` 中 `ClusterSize > 1` 的内核一律置为不可杀（Level-1 边界）。代价：Cluster 内核失去内核内抢占（本阶段测试的 PyTorch 生产算子均未使用 Cluster）。
- **DEF-22**：`BinaryHasDeviceCalls` 识别 `CALL.ABS.NOINC`（低 12 位 `0x343`）。
- **DEF-23**：`ConfiguredLmemCapBytes()` 改为：无调用 → 静态局部内存大小；有调用 → 静态 + `CU_LIMIT_STACK_SIZE`（插桩时读取；默认 1024 B），超过此深度内核自身就会栈溢出。

| 内核（RTX 5060，Lv3） | 修复前 | 修复后 |
|---|---|---|
| LayerNorm / RMSNorm（`CALL.REL`） | cap 4096 B/线程，arena 230.9 MiB | cap 1024 B/线程，arena 102.6 MiB |
| `reduce_kernel` / `direct_copy`（`CALL.ABS`） | calls=0，**无栈保存区**（DEF-22），arena 25.6 MiB | calls=1，cap 1024 B/线程，arena 102.6 MiB |
| GEMM（无调用） | 21.2 MiB | 不变 |

## 3. DEF-17：Entry Guardian 开销

### 3.1 问题定位（对照实验，RTX 5060，相对 native）

| 构建 | `transpose_copy` | `rope_apply` | 说明 |
|---|---:|---:|---|
| Lv1 | +0.1% | −0.1% | 无插桩 |
| Lv3，插桩后强制走 Guardian 旁路（实验） | **+0.0%** | **+0.4%** | 代码搬移本身无开销 |
| Lv3 原始 Guardian（v1） | +28.3% | +18.7% | |
| Lv3 去掉屏障后 `entry_dec` 读取（**不安全，仅测上限**） | +17.6% | +6.8% | |

结论：开销全部来自 Guardian 逻辑。原手写指令的控制字让每条可变延迟指令（`LDC`/`S2R`/`LD`）都等待前一条完成（`&req={1,0}`），Guardian 中 4 次 L2 读取完全串行；此外上万个 CTA 同时读取同一 32 字节控制头造成 L2 热点。

### 3.2 三个版本（锚点 0x270 / 0x2c0 / 0x3b0 / 0x4c0 均不变）

| 版本 | 开关 | 内容 |
|---|---|---|
| 原始 v1 | `XSCHED_SM120_GUARDIAN_V1=1` | 全串行发射；slot 28 重读 `cmd` |
| **默认（本阶段上线）** | 无 | 全串行发射；**slot 28 不再重读 `cmd`**，复用之前读到的值 |
| 实验 v2 | `XSCHED_SM120_GUARDIAN_V2=1` | 默认版本 + 控制头两次读取在 SB2/SB3 上并行发射 + `S2R/LDC` 链在 SB2–SB5 上并行发射（子开关 `_V2_SERIAL_HDR` / `_V2_SERIAL_SREG`） |

去掉重读的正确性：读到 `cmd == 0` 的 CTA 必然在主机发布 `cmd` 之前已驻留，而 BAR0 脉冲在该写入完成后才触发，因此该 CTA 要么已完成、要么会被 Trap 并按 Guardian 区间规则处理；与 v1 在数十个周期后重读的保证相同。

### 3.4 为什么实验 v2 不作为默认：LLM-08 二分（RTX 5080）

全量回归中 `LLM-08`（同一进程两条 Lv3 LP 队列 + 一条高优先级 HP 流）首次出现 `e2=nan`。逐项开关二分：

| 配置 | LLM-08 失败 |
|---|---:|
| v2 全部特性（含 1 KiB / 4 KiB LMEM 上限、自旋开/关、`CALL.ABS` 检测开/关） | **11 / 61** |
| v2 + 恢复 slot 28 重读 | 1 / 12 |
| v2 + 串行控制头读取 | 0 / 12 |
| v2 + 串行 `S2R/LDC` | 0 / 12 |
| 原始 v1（各种组合） | 0 / 54 |
| **默认（串行 + 去重读）** | **0 / 24** |

失败需要异步发射窗口（与重读无关）。推测机制：BAR0 脉冲对设备上所有驻留 CTA 生效，另一条队列的 CTA 作为“旁观者”被 Trap 后直接返回；若 Trap 恰在 Guardian 异步发射的 `LD/LDC/S2R` 尚未完成时送达，而这些指令的目的寄存器（R0–R10）正是 Trap 处理程序保存在 112 B 硬件帧并用作暂存的寄存器，则恢复后可能读到旧值（如把 `is_restore_wave` 误判为非零而走恢复路径退出，CTA 工作被丢弃 → 输出未初始化 → NaN）。旁证：恢复波次中的 `BPT.TRAP 0x1` 自陷是 SM 级事件，会把同一 SM 上驻留的其他 CTA（包括另一条队列的内核）“伴随”拉入 Trap（技术手册 §5 Cave 1 的 Collateral Trap 处理）；LLM-08 中两条 Lv3 队列频繁恢复，伴随 Trap 命中另一队列 CTA 的 Guardian 异步窗口的机会远多于单队列测试，这与只有 LLM-08 失败的现象一致。该机制尚未用硬件实验证实，因此按“正确性优先”只把它作为实验开关保留。

### 3.5 未采用的方案
用 `BAR.RED.OR` 在屏障处广播线程 0 的排空决定可省掉屏障后的 `entry_dec` 读取（上限：`rope` → +6.8%、`sort` → +5.3%），但 Trap 是否保留屏障归约结果尚未表征，错误时会静默丢弃 CTA 工作，不上线。

### 3.6 短 CTA 路由（默认开启）

Guardian 的固定成本（控制头首读 + `BAR.SYNC` + 屏障后读取）按 CTA 计；CTA 越短，占比越高。对 Suite 7 中所有内核做 SASS 分析（`XSCHED_SM120_DUMP_DIR` 导出 + `nvdisasm`）：开销最高的内核全部是**无回边**的逐元素内核——`transpose_copy` / `rope_apply` 使用的 `elementwise_kernel<128,4>`（1.6–3.3 万个 CTA）、`gelu` / `rope` 的 `vectorized_elementwise_kernel`（1.6–8.8 万个 CTA）；而归约、CUB 排序、GEMM、Norm 等有循环的内核 CTA 较长，Guardian 成本可忽略。

规则（`cuda_queue.cpp`，`kRouteLv1ShortCta`）：内核**无回边且无间接跳转**（`BinaryIsLoopFree()`：`BRA` 偏移 < −16 即回边，忽略 `EXIT` 后的“自跳”填充；`BRX` 视为可能成环）、**无函数调用**，且网格在 `[MIN_WAVES, MAX_WAVES]` 波（默认 2–1024 波，波 = SM 数 × 每 SM 驻留块数）之间 → 走 Level-1 边界。无回边保证每个线程每条指令至多执行一次，即 CTA 时长有界；波数上限保证“等内核结束”的延迟有界。开关：`XSCHED_SM120_SHORT_CTA_LV1=0` 关闭，`XSCHED_SM120_SHORT_CTA_MIN_WAVES` / `_MAX_WAVES` 调整窗口。

`BRA` 相对偏移的编码由 3,653 条分支（PyTorch / cuBLAS / CUB 内核）拟合得到并全部吻合：偏移 / 4 = `w0[16:24] | W[34:74] << 8`（有符号，相对下一条指令）。

| 算子（相对 native 批量延迟，每项 3 轮 × 3 次中途抢占） | 5060 路由关 | 5060 路由开 | 5080 路由关 | 5080 路由开 | HP P50 5060 关→开 (ms) | HP P50 5080 关→开 (ms) |
|---|---:|---:|---:|---:|---:|---:|
| `transpose_copy` | +17.9% | **+0.3%** | +53.6% | **−0.1%** | 1.09 → 2.37 | 0.69 → 0.54 |
| `rope_apply` | +17.6% | **+1.9%** | +56.6% | **+3.2%** | 0.66 → 0.43 | 0.58 → 0.33 |
| `gelu_tanh` | +0.4% | +0.7% | +0.1% | +0.0% | 1.26 → 0.53 | 0.79 → 0.82 |
| `embedding` | +2.0% | +1.6% | +1.1% | +1.2% | 0.57 → 0.55 | 0.28 → 0.28 |
| `softmax` / `sort_16m` / `topk` / `batchnorm` | 不路由（有循环或波数不足），开销与路由关相同 | | | | | |

全部比特一致。代价在 `transpose_copy`（5060 上单个内核 2.3 ms）：Level-1 只能在内核边界让出，HP P50 从 1.09 ms 升到 2.37 ms；而 `rope` / `gelu` 由于 Mode 5 驱逐数万个 CTA 本身较慢，改走 Level-1 后挂起反而更快。需要严格亚毫秒抢占的部署可以关闭路由或调低 `MAX_WAVES`。

与回归测试的关系：Suite 1/4、合成测试与验收组用于验证 Mode 5 **机制**，路由会把部分被测内核（例如 cuFFT 的 17.5 KB 全展开内核）移出 Mode 5，这些测试就不再验证 Mode 5。因此回归计划对这些机制套件设置 `XSCHED_SM120_SHORT_CTA_LV1=0`；Suite 7 同时运行默认 Lv3（路由开）与 `lv3m5`（路由关，纯 Mode 5）两种模式（§6）。

### 3.7 `BAR.RED` norm_gate（默认开启）：去掉屏障后的 `entry_dec` 读取

§3.1 的上限实验表明，屏障后的 `entry_dec` 读取是有循环的短 CTA 内核（`sort` / `topk`）剩余开销的主要部分，但当时担心“Trap 是否保留屏障归约结果”而未采用。重新分析 Cave 0 的处理逻辑后，方案如下：
- slot 39 的 `BAR.SYNC 0` 改为 `BAR.RED.OR 0, P0`，归约输入是已有的 `P0 = (tid == 0 && cmd != 0)`，即“线程 0 决定排空并写了 `entry_dec`”；slot 40 `B2R.RESULT RZ, P1` 取回结果；slot 41 `@P1` 才读取 `entry_dec`；slot 42 `P0 = (entry_dec != 0) && P1`；slot 43 `@P0 EXIT`；slot 44 跳到原内核。
- 正确性：`entry_dec` 只可能由本 Guardian（结果必为真）或 Trap 处理程序写入；而 Trap 处理程序从不完成这个屏障——被 BAR0 脉冲打断的 warp（包括正在屏障等待的）都在 Cave 0 中按 `entry_dec` 决定，并在自己的 `bar_sync_trap` 上同步。屏障完成后、`B2R` 之前被 Trap 并作为 State B 恢复时，`B2R` 的值不确定，但此时 `entry_dec == 0`，两种结果都会走“运行”路径，因此仍然正确。
- 布局：屏障后需要多一个槽位，`restore_path` / `replay_state_c` 各后移一槽（0x2c0 → 0x2d0、0x3b0 → 0x3c0），删去 replay 区的填充 NOP，replay 屏障（0x4c0）与 Guardian 大小（0x500）不变；锚点改为 Guardian 与 Trap 引擎共用的运行时函数。`BAR.RED.OR` / `B2R.RESULT` 的编码取自 nvcc 输出，并用 `nvdisasm` 验证了自构造的谓词字段。
- 开关：`XSCHED_SM120_GUARDIAN_BARRED=0` 恢复 `BAR.SYNC`；`XSCHED_SM120_GUARDIAN_V1=1`（原版 Guardian）同时关闭它。默认布局下的 Guardian 字节与之前完全相同（已比对）。

验证（启用前）：5060 合成 Trap 测试、收敛/压测、`C1` ×10、Suite 1 子集、`LLM-08` ×12、`dnn06`、Suite 7 算子全部通过；5080 62/62 通过，其中 `LLM-08` 36/36（实验 v2 在同一用例上 11/61 失败）。全部比特一致。

|---|---:|---:|---:|---:|
| `sort_16m` | +14.8% | **+8.0%** | +15.6% | +14.8% |

## 4. 每调用提交开销

### 4.1 原因
XQueue 的每次调用有两次线程交接：应用线程把命令交给 LaunchWorker（若工作线程已休眠需一次 futex 唤醒），`WaitAll` 时由工作线程同步硬件流后再唤醒应用线程。Suite 7 的算子耗时 0.15–2.4 ms，远超自旋窗口，两次交接都退化为 futex 唤醒（各约 4–5 µs）。Lv3 另有每次发射约 2.7 µs 的驱动调用（控制头布局 HtoD 拷贝 1.1 µs、`cuXtraSetDebuggerParams` 等）。

### 4.2 改动（`preempt/src/xqueue/*`，默认开启）

| 机制 | 内容 | 开关 |
|---|---|---|
| 有界自旋 | 工作线程与等待方在条件变量前自旋 ≤ 30 µs | `XSCHED_SPIN_US`（0 关闭） |
| **直接提交** | 若队列中没有排队命令、工作线程未持有未处理的硬件命令、处于运行态、无在途命令，且**工作线程已休眠**（唤醒需要 futex）**或上一次调用（两次 `WaitAll` 之间）只有 1 个命令**，则由提交线程在工作线程锁下直接发射。多命令调用在工作线程醒着时仍交接（保留与应用线程的流水并行）。仅 `DirectLaunchable()` 的命令（CUDA 内核）参与；`CommandBuffer` 闸门保证顺序；就绪事件照常发给调度器 | `XSCHED_XQUEUE_DIRECT` |
| **调用方 `WaitAll`** | 所有已提交命令均已发射时，等待线程自己 `cuStreamSynchronize`；若同步期间发生挂起（`pause_count_` 变化）或工作线程处于暂停态，回退到原路径 | `XSCHED_XQUEUE_CALLER_SYNC` |
| 后台批同步前自旋 | 工作线程在开始阻塞式后台批同步前先等一个自旋窗口，避免紧随其后的命令被挡在同步之后 | 随 `XSCHED_SPIN_US` |
| **控制头布局缓存** | 同一流上布局 36 B 与上次相同则跳过 HtoD 拷贝（设备代码从不写这些字段；控制头重分配会改变地址） | `XSCHED_SM120_LAYOUT_CACHE` |
| 修正 `SyncAllWithLock` | 原实现在同步后把**所有**在途命令标为完成；直接提交下同步窗口内可能有新发射的命令，现只完成同步开始前已发射的命令 | — |

被否决的尝试：调用方 `WaitAll` 清空队列后由调用线程立即把队列标为空闲并发送 Idle 事件（以便下一次调用走直接提交）。5060 上“长内核”模式反而从 +1.9/+2.9 µs 变为 +4.0/+5–7.6 µs（调度器事件发送进入关键路径），已回退。

### 4.4 PERF-2：未受管流的透传发射

现象：Suite 8 中即使 `request` 策略在 HP 请求期间完全挂起 LP，5080 上 HP 的 TPOT 仍为无 XSched 时的 1.23×；而且这一差距在 LP 线程启动之前（同一进程内测得的 solo TPOT）就已存在，说明与 LP、GIL 和调度策略无关。5060 上只加载 shim、不创建任何 XQueue，HF decode 每步就慢约 1.3 ms（8.41 → 9.77 ms）。

定位：在以 decode 为主的运行上做 `perf` 采样，`cuXtraKernelGetFunction`（把 CUDA 12 的 `CUkernel` 句柄转换为当前上下文的 `CUfunction`）占全部样本的 **8.4%**，与真正的驱动发射（12.5%）同一量级；它在每个内核命令的构造函数中被调用，透传发射也不例外。微基准里的“1 个小内核”发射没有暴露这一点，因为同一个函数句柄的转换在驱动内有缓存，而 decode 每步发射数百个不同的内核。

修复：
- 内核命令只有在进入 XQueue（需要深拷贝参数）时才在构造函数中解析 `CUfunction` 和参数个数；透传命令 `kFuncHandle == nullptr`，通过 `FuncHandle()` 按需解析（Level-2 插桩路径与发射重试路径改用 `FuncHandle()`）。
- sm120 透传发射原本每次都调用 `cuXtraSetDebuggerParams` 清零 Guardian 参数。现在只有该发射句柄对应的函数可能持有非零 Mode 5 参数时才解析并清零（按发射句柄登记，`MaybeParamsSet()`）；检查与发射仍在上下文 `LaunchMutex` 内，LP 的 Mode 5 发射不会插入其间。`XSCHED_SM120_ALWAYS_CLEAR_PARAMS=1` 恢复每次清零。
- `DirectLaunch()` 中“流所属上下文 / 设备架构”的查询按线程缓存。

结果（5060，`ppl` LP，同一进程内 LP 启动前测得的 solo TPOT）：无 XSched 8.61 ms；修复后 Lv1 8.76 ms、Lv3 8.72 ms、仅 shim 8.94 ms（+1.3–3.8%；修复前仅 shim 为 9.77 vs 8.41 ms，+16%）；`request` 策略下服务 TPOT 8.83 / 8.78 ms，与进程内 solo 相同。两卡最终数据见 §5 / §6。

### 4.5 arena 空闲回收（显存）

Mode 5 的 arena（驱逐时保存寄存器/共享内存/局部内存的显存池）原来按流取历史最高水位常驻，且因增长而被替换的旧 arena 直到流上下文销毁才释放。现在 `CudaQueueLv3Trap::Synchronize()` 之后（流刚空闲）调用 `TrimArenas()`：
- 条件：同步开始后没有新的发射（发射序号不变），且没有待恢复的驱逐状态（`saved_arena_dev_ == 0`、不在恢复波次）；
- 立即释放因增长而被替换的旧 arena；
- 当前 arena 若在连续 64 次同步的窗口内始终大于最大需求的 2 倍且大于 `XSCHED_SM120_ARENA_TRIM_MIN_MB`（默认 64 MiB），则释放，下次发射按需重新分配（窗口与阈值避免大小内核交替时反复分配）。`XSCHED_SM120_ARENA_TRIM=0` 关闭。

验证：大网格 LayerNorm 把 arena 撑到 61.7 MB 后，200 次小调用（需求 22 MB）期间在第一个窗口结束时释放（阈值设 1 MiB 的测试配置），结果正确；回归计划新增两项在 1 MiB 阈值下运行的抢占测试（`SYN-stress-trim`、`S6-llm08-trim`），使释放路径与驱逐/恢复交错执行。

`request` 类策略在 HP 请求期间完全挂起 LP，所以 LP 吞吐上限为 `1 − HP 占空比`（HP 请求活跃时间占比，Suite 8 记录为 `hp_duty_pct`）。原负载（平均间隔 500 ms）下 HP 占空比 26–44%，上限为 56–74%；Lv1 `request` 实测已贴近上限（5060：67% vs 65%）。要超过 80%，LP 必须在 HP decode 期间与之共置，而共置（`prefill` 策略、native 流优先级）会使 TPOT 上升 9–92%。因此该目标与负载相关，不是策略缺陷。Lv3 的 LP 低于上限 10–15 个百分点，来自 LP 自身的 Lv3 稳态开销与每次驱逐/恢复的成本。

### 5.3 空间共享：在原负载下突破 `1 − 占空比` 上限的尝试

时间共享（挂起 LP）的上限是 `1 − HP 占空比`。为检验能否在原负载（占空比约 30–38%）下同时满足两个目标，Suite 8 新增 `--lp-sms`：用 CUDA green context（`cuDevSmResourceSplitByCount` + `cuGreenCtxCreate`）把 LP 限制在一部分 SM 上，HP 在主上下文的高优先级流上运行，不挂起 LP。可行性先验证：green context 流可直接被 PyTorch（`torch.cuda.ExternalStream`）使用，4096² BF16 GEMM 在 8 / 16 / 24 个 SM 上分别慢 3.66× / 1.82× / 1.24×（理论 3.75 / 1.88 / 1.25），结果比特一致；SM 数有分配粒度（5060 上 20–24 均得到 24 个）。目前仅支持 native 模式（XSched 透传路径要求流所属上下文等于当前上下文，green context 流不满足）。下表来自上一轮完整回归中的同一组运行（本轮未改动空间共享相关代码）。

| # | 问题 | 后果 | 处理 |
|---|---|---|---|
| T-16 | 自写微基准中内核写 `out[1024+b]`，而缓冲区只有 4 KiB | 越界写落到相邻的 XSched 控制内存，后续 CTA 在 Guardian 中误判退出，看上去像“Lv3 下循环内核出错” | 修正缓冲区；同时记录观察 **OBS-13**：用户内核的越界写可破坏 XSched 的设备端控制结构（与任何同进程设备分配相同，属固有风险） |
| T-17 | 每个新内核首次发射时的插桩（约 19 ms）被计入 8 次平均 | 看上去“Lv3 下事件计时每次多 2.4 ms” | 排除首次发射；事件计时经复核正确 |
| T-18 | 生产路由策略会把机制测试的被测内核移出 Mode 5 | 机制测试不再覆盖 Mode 5（首轮 `LIB-06` 失败起初被归因于此，关闭路由后仍失败，实际原因见 T-19） | 机制套件关闭路由；Suite 7 增加 `lv3m5` 列 |
| T-19 | `LIB-06` 的 LP 工作只有一次 cuFFT（< 1 ms），而测试在 800 µs 后才尝试抢占；旧提交路径较慢时才“恰好”能抢到（5060 上 1/2） | 提交路径加速后 LP 在抢占窗口前结束，`preempts=0/2` 判失败（两卡，与路由无关） | LP 与参考均改为 4 次原地前向 FFT（仍非幂等），比较改为逐元素按位相等；同时给该文件全部 23 处可分页 H2D 拷贝补 `cudaDeviceSynchronize()`（T-11 同类竞态）。Suite 1 与验收组用修正后的二进制重跑（§6） |
| T-20 | 用“1 个小内核反复发射”的微基准评估透传开销 | 驱动对同一函数句柄的 `CUkernel→CUfunction` 转换有缓存，微基准显示透传几乎零开销，而真实 decode 每步发射数百个不同内核，开销达 1.3 ms/步（PERF-2） | 以真实负载的 `perf` 采样为准；微基准保留用于 XQueue 交接路径 |

## 9. 剩余事项

3. arena 跨流共享（空闲回收已在 §4.5 完成）。
4. DEF-19 Cluster 内核的完整支持。可行方案是“Cluster 级排空”而不是保存 Cluster 状态（集群屏障相位与 DSMEM 映射不在 Trap 帧中，也无法从软件恢复）：Guardian 以 `barrier.cluster` + DSMEM 广播 rank 0 的决定，使同一 Cluster 的全部 CTA 一致地“排空（State C）或运行”；已在运行的 Cluster 不驱逐（Trap 时作为旁观者直接返回），抢占延迟上限为单个 Cluster 的时长。需要新的 Guardian 变体与 `UCGABAR_*` / `MAPA` 的 SASS 编码，属于 Phase 3.4 工作量。路由策略的自适应（按实测内核时长而非静态波数）。
5. DEF-10 非 root BAR0、DEF-09 图内抢占、HP/LP 多进程服务测试、更大模型与基线对比（Phase 3.4 / 3.5）。
