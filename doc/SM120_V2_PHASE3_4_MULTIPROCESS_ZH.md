# Phase 3.4-2：HP / LP 多进程服务测试与跨进程调度（DEF-26 / 27 / 28）

> 日期：2026-11-26 · 分支 `phase3-def20-production-testing` · 硬件：RTX 5060（本地，同时驱动桌面）、RTX 5080（共享服务器，无显示）
> 结论：
> 1. **OBS-7 得到证实**：把 HP 与 LP 放进两个进程后，按请求挂起 LP 时 HP 的 TPOT P50 两卡均为 solo 的 **1.00×**（单进程 Suite 8 为 1.02–1.07×），残余膨胀来自单进程内的 GIL 争用。
> 2. 新的多进程测试发现：**DEF-26**（调度器执行线程没有 CUDA 上下文，跨进程模式下 Lv3 恢复断言失败，已修复）、**DEF-27**（跨进程透明调度下 Lv3 Trap 与 GPU 时间片上下文切换冲突，触发 Xid 109 `CTX SWITCH TIMEOUT`；已缓解：默认改走 Level-1 边界）、**DEF-28**（`xserver` 收到 SIGTERM 不清理 IPC 消息队列，换用户再启动时客户端阻塞，已修复）。曾登记的 **DEF-25 已撤回**：属于测量误判，为它做的改动引入了新问题，已回退（§2.1）。
> 3. 另记录 **OBS-8**：在同时驱动桌面的 RTX 5060 上，Lv3 多波次压测开始时两次出现桌面图形进程的 Xid 31 MMU 故障（进程未崩溃）。

## 1. 测试方法

新脚本 `test/sm120_v2/eval/bench_mp_serving_p34.py` 与 Suite 8 使用完全相同的负载（Qwen2.5-0.5B 真实权重、20 个对话请求、泊松到达平均间隔 500 ms、每请求 16 个 token 贪心解码；LP 为 `ppl` 困惑度评估或 `prefill` 打分），区别是 **HP 与 LP 是两个独立进程**（两个 CUDA 上下文，GPU 在两者间时间片轮转）。每个 HP token 序列都必须等于 solo 金标准，每次 LP 迭代都必须比特一致。

| 模式 | 含义 |
|---|---|
| `solo` | 只有 HP 进程 |
| `native` | HP + LP 两个进程，不加载 XSched |
| `req-lv1` / `req-lv3` | LP 进程的流是 XQueue（Level-1 / Level-3）；HP 进程每个请求前通过 Unix socket 请 LP 进程挂起队列，**收到“已挂起”确认后**才开始请求，结束后恢复（应用层跨进程 `request` 策略） |
| `glb-lv1` / `glb-lv3` | XSched 全局调度器：`xserver`（HPF 策略）+ 两个进程 `XSCHED_SCHEDULER=GLB`；HP 流为优先级 1 的 Level-1 XQueue，LP 队列优先级 0；调度路径中没有任何应用代码（完全透明） |

TPOT 比值以同一进程内 LP 空闲时背靠背测得的 solo TPOT 为分母（与 Suite 8 相同）。注意：RTX 5060 上 `solo` 模式本身（请求之间 GPU 空闲 0.5 s）的 TPOT 为背靠背值的 1.18×，因为 GPU 在空闲间隙降频；共置模式下 LP 让 GPU 保持高频，所以 TPOT 可以低于 `solo` 行。RTX 5080 无此现象。LP 吞吐的理论上限（按请求挂起）为 `1 − HP 占空比`。

## 2. 发现的缺陷

### 2.1 DEF-25（已撤回：测量误判）及其教训

最初的测试在 `stream.synchronize()` 返回后**立即**查询 `XQueueQuery`，Level-1 队列 200/200 次仍为 Ready，于是判定“调用方 `WaitAll` 快速路径（PERF-1）不做 Ready → Idle 转换，调度器会认为队列永远忙”，并让调用线程在同步成功后直接把队列标为 Idle。

这个结论是错的。发射线程在命令缓冲区排空后会自行生成一次后台同步与 `WaitAll`，并完成 Ready → Idle 转换（同时发出 `XQueueIdleEvent`）。改为轮询后实测：同步返回后 **约 21 µs（最大 41 µs）** 队列即为 Idle，200/200。对调度器而言这个延迟可以忽略。

而那个“修复”本身有害：命令缓冲区约定“Idle 时最后入队的命令一定是已完成的 `WaitAll`”，`EnqueueXQueueWaitAllCommand()` 据此在 Idle 时直接返回、不再等待。调用线程置 Idle 打破了这一约定，并与发射线程仍在进行的后台同步竞争，导致全量回归中 `HW-05`（空闲队列挂起 / 恢复）两卡均断言失败；5080 上 `S8-ppl-lv3-prefill` 还出现 1 次 LP 迭代结果不一致（403 次中 1 次）。改动已完全回退：`HW-05` 3/3 通过，该 S8 配置在 5080 上重复 12 次（约 4,800 次 LP 迭代）0 错，5060 结果见 §4。此前各轮全量回归中该配置约 1 万次迭代同样 0 错，与“不一致由已回退的改动引起”相符，但单次事件不足以证明。

`test_xqueue_idle_p34.py` 改为检查“每次同步后 50 ms 内变为 Idle、新提交后变回 Ready”，并输出转换耗时，作为回归项 `SYN-xq-idle` 保留。

教训（T-22）：状态类测试要区分“立即”与“最终”语义，先测清楚异步转换的耗时再下缺陷结论；任何绕开既有组件改状态的修复，都要先找出该状态的全部读者及其约定。

### 2.2 DEF-26：调度器执行线程没有 CUDA 上下文（已修复）

全局 / 本地调度器在其执行线程上调用 `XQueueSuspend` / `XQueueResume`。该线程没有当前 CUDA 上下文。Level-1 的恢复只唤醒发射线程，不受影响；Level-3 的 `Reactivate()` 要重新发射被中断的内核并准备恢复（分配 / 写控制内存），在该线程上失败：`Assertion failed: sm120 PrepareLaunch failed`，LP 进程退出。修复：`CudaQueueLv3Trap::{Deactivate, Interrupt, Reactivate}` 在调用线程没有队列上下文时临时压入该上下文。

### 2.3 DEF-27：跨进程透明调度下 Lv3 Trap 与上下文切换冲突（Xid 109，已缓解）

修复 DEF-26 后，`glb-lv3` 每次运行仍出现一次 **Xid 109 `CTX SWITCH TIMEOUT`**（LP 进程），驱动随后的恢复使**两个进程同时**报 `cuda error 719`，HP 有请求被阻塞约 4.3 s，LP 吞吐降到 13–32%。内核日志中 4 次 Xid 109 全部来自 `glb-lv3` 运行，`req-lv3` 与其他模式 0 次。

机制：HP 与 LP 是两个上下文，GPU 按时间片在两者间切换。全局调度器下 HP 一变为 Ready 就继续发射内核，同时调度器异步挂起 LP；若 GPU 对 LP 上下文的时间片切换请求恰好在 LP 线程束处于 Trap 处理程序中时到达，该上下文无法被切出，切换超时（约 300 次挂起中出现一次，即约 0.3%/次）。`req-lv3` 中 HP 等到 LP 的驱逐确认后才发射，竞争不存在；单进程内 HP 与 LP 共用一个上下文，也不存在。

缓解：`XSCHED_SCHEDULER=GLB` 时 SM120 内核默认走 Level-1 边界（新增路由原因 `lv1_glb_sched`，告警一次；`XSCHED_SM120_GLB_LV3=1` 可强制 Lv3）。根本修复需要以下之一：全局调度协议增加“低优先级队列已驱逐”的确认，HP 收到后再发射；或通过 RM 控制把 LP 上下文的计算抢占模式设为 CTA / WFI、加长其时间片（代码中已有 `NV2080_CTRL_CMD_GR_SET_CTXSW_PREEMPTION_MODE` 与 `NVA06C_CTRL_CMD_SET_TIMESLICE` 的调用，但在 Python 进程中需要先解决 RM 句柄捕获）。两者都未在本轮实现，DEF-27 保持开放。

一般性提示：只要另一个进程的上下文在 Lv3 驱逐期间积极争用 GPU，就存在同样的竞争；早先的旁观进程测试（60 次脉冲）未遇到，与约 0.3% 的概率相符。

### 2.4 DEF-28：`xserver` 未处理 SIGTERM，残留 IPC 队列使后续运行挂起（已修复）

`xserver` 只在 SIGINT / SIGQUIT 时清理其 IPC 通道（SysV 消息队列，键 `0x1`）；被 SIGTERM（`kill`、systemd、测试脚本的 `terminate()`）结束时队列残留。全量回归以 root 运行 Suite 9 后，留下一个 root 所有、含 439 条未读消息的队列；随后以普通用户启动的 `xserver` 无法删除它（`Operation not permitted`），客户端持续向这个无人接收的队列发事件，队列满后发送阻塞在内核发射路径里，进程挂起直至超时（5060 上 `glb-lv1` / `glb-lv3` 各挂 600 / 900 s）。

修复：`xserver` 同时处理 SIGTERM（实测结束后队列被删除）；测试脚本改用 SIGINT 结束 `xserver`，并在启动前检查键 `0x1` 的队列是否属于其他用户，是则给出 `ipcrm` 提示后退出，而不是挂起。客户端在服务端消失时阻塞而非报错，属于上游设计，记录为已知风险。

教训（T-23）：同一台机器上 root 与普通用户交替运行使用 IPC 的测试时，要确认每个进程退出时都清理了 IPC 对象。

### 2.5 OBS-8：显示 GPU 上桌面图形进程的 Xid 31

RTX 5060 同时驱动桌面。本周内核日志中有 4 条桌面进程的 Xid 31（`MMU Fault: ENGINE GRAPHICS GPC2 GPCCLIENT_GCC faulted @ 0x0`）：

| 时间 | 进程 | 当时的测试 |
|---|---|---|
| 11-25 20:14:05 | `ghostty`、`gnome-shell` | 本会话日志之前，无法对应 |
| 11-26 00:31:23 | `ghostty` | `SYN-stress-g8`（00:31:22 开始的 Lv3 多波次压测） |
| 11-26 06:15:39 | `gnome-shell` | DEF-10 代理重启压测（06:15:38 开始） |

两次可对应的事件都发生在多波次压测开始后约 1 s 内，提示 BAR0 广播脉冲偶尔会打断同时运行的**图形**上下文（早先的旁观测试只覆盖计算上下文）。两个进程的 pid 前后不变，即没有崩溃。按数千次压测脉冲计，这是罕见事件，但**在驱动显示器的 GPU 上使用 Lv3 时应预期桌面偶发故障**；生产部署建议用无显示的 GPU。RTX 5080（无显示）上本轮未见新的 Xid。

## 4. 回归

两卡全量回归（最终构建，以 root 运行；`regress_p3.py --suites full` + 低负载组，新增 `SYN-xq-idle` 与 Suite 9）：**RTX 5060 288/288、RTX 5080 288/288**。Suite 7 Lv3 两卡 29/29 比特一致（默认与纯 Mode 5 两种配置），Lv3 批量开销中位数 +0.4% / +0.3%，最高 +4.0% / +4.9%（均为 `topk_sampling`）。Suite 9（root，直接映射 BAR0）两卡 6/6：`req-lv3` TPOT P50 1.00×、LP 59% / 68%；`glb-lv1` 的 TPOT P99 这一轮为 1.42× / 1.28×，高于 §3 的单轮结果（见 §3 要点）。`SYN-xq-idle` 两卡通过（同步后约 21 µs 变为 Idle）。回归结束后两卡均无残留 IPC 消息队列；5060 内核日志无新的 Xid；5080 上 0 次让路。证据：[`evidence/phase3_4_mp_20261126/`](evidence/phase3_4_mp_20261126/)。
