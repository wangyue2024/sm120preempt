# Phase 3.5：第一梯队——Level-3 的价值、CUDA Graph 图内抢占（DEF-09）、vLLM 与 7B 模型

> 日期：2026-11-26 · 分支 `phase3-def20-production-testing` · 硬件：RTX 5060（本地，同时驱动桌面，驱动 595.99.02）、RTX 5080（共享服务器，无显示，驱动 580.95.05）
> 配套：原理与实现细节见 [`SM120_V2_PHASE3_PRINCIPLES_AND_IMPLEMENTATION_ZH.md`](SM120_V2_PHASE3_PRINCIPLES_AND_IMPLEMENTATION_ZH.md) §5.1（图展平）、§5.2（跨流事件等待）、§5 末（按时长的短 CTA 路由）；缺陷台账 §10.12。
>
> 结论：
> 1. **Level-3 的价值边界已量化**（§2）。同一进程内、HP 走高优先级流时，只要 LP 内核留有 SM 空位，GPU 的共驻（co-residence，OBS-16）就让 native 的小 HP 请求已经很快（P99 0.3–1.8 ms）；此时 Level-3 多数情况下更低（5080 cuBLAS GEMM 0.89 → 0.45 ms，SDPA 0.46 → 0.32 ms），在部分占用的持久化 GEMM 上反而略高 0.1–0.4 ms（挂起本身的代价）。**LP 占满 SM 时**，native 的 HP P99 随 LP 内核时长线性增长（5060 12.7 / 26.6 ms，5080 4.0–19.4 ms），Level-3 保持在 **0.4–2.5 ms，与 LP 内核时长无关**。较大的 HP 请求（需要更多 SM）在 SDPA 上 native 6.5 / 2.7 ms → Level-3 2.6 / 1.2 ms（5060 / 5080）。Level-1（等在飞内核）在所有负载上都随 LP 内核时长线性增长（最长 370 ms）。
> 2. **CUDA Graph 图内抢占（DEF-09）完成**（§3）：图在 Level-3 队列上按节点展平提交，非幂等的整网捕获训练步在 15 次挂起下与原生重放比特一致，挂起 P99 从 407 ms（图边界）降到 0.4–1.4 ms；新增按时长展平（`XSCHED_CUDA_GRAPH_FLATTEN_MIN_US`）。
> 3. **vLLM 0.34 + Qwen2.5-0.5B / 3B / 7B-AWQ 在 XSched 下运行**（§4），抢占下 32/32 条贪心输出与原生一致。过程中发现并修复 4 个问题：**DEF-29**（跨流事件等待阻塞调用线程，vLLM 吞吐 −22%）、**DEF-30**（短 CTA 路由放行毫秒级内核，Lv3 尾延迟 2–3 ms）、**DEF-31**（Lv3 恢复会重放非 killable 命令）、**DEF-32**（整图发射的内核节点继承同函数上一次 Mode 5 发射的 Guardian 参数窗口，被当作那次发射驱逐 / 排空而不再恢复——vLLM 不展平时输出错误）；以及一个被否决的设计（GPU 等待主机标志，与驱动锁死锁）。
> 4. vLLM（RTX 5080）：7B-AWQ prefill 为主的负载 HP P99 native 4.1 ms、Level-1 9.6 ms、**Level-3 1.4 ms**；7B decode native 3.4 ms、Level-1 7.2 ms、**Level-3 1.1–2.6 ms**；3B prefill native 0.52、Level-1 10.4、Level-3 0.60 ms。Level-3 的代价主要是图展平的每节点 CPU 开销（7B decode −20%，prefill −11%–−16%，0.5B decode −36%）。
> 5. 收尾回归中另发现 **DEF-33**：进程退出时 Trap 引擎在静态析构里把原处理程序写回已被拆除的上下文，libcuda 堆损坏（5080 LIB-12 进程退出时 18/20 次崩溃，计算本身正确）。已修复。

## 2. Level-3 的价值（第一梯队 2）

### 2.1 方法

脚本 `test/sm120_v2/eval/bench_lv3_value_p35.py`。一个 LP 线程在 XQueue 流上循环执行一个长内核，每次迭代都与独占运行的结果做比特比较（`torch.ne(...).any()` 累加到一个标志，不做类型转换，队列深度 ≤ 4）；HP 线程按固定间隔到达，在高优先级流上执行一个小（约 0.4 ms）或大（约 2 ms）的 GEMM 链，并与金标准比较。

| LP 负载族 | 内核 | 特点 |
|---|---|---|
| `gemm` | cuBLAS GEMM（BF16，N×N） | 多波 CTA，波与波之间留出 SM 空位 |
| `persistent` | Triton 持久化 GEMM，网格 = SM 数，BM=BN=128、BK=32、2 级流水 | 每个 SM 一个 CTA，但寄存器 / 共享内存只占一部分 |
| `persistent-full` | 同上，BK=64、3 级流水（约 96 KB 共享内存） | 每个 SM 被占满，HP 无法共驻 |
| `sdpa` | `scaled_dot_product_attention` flash 前向（长序列 prefill） | 访存与计算混合 |

| 模式 | 含义 |
|---|---|
| `native` | 不加载 XSched，HP 走高优先级流 |
| `lv1` | LP 为 Level-1 XQueue，HP 到达时 `XQueueSuspend(xq, 0)`（不等在飞命令） |
| `lv1-sync` | Level-1，挂起时等在飞命令完成（HP 获得独占 GPU 的标准做法） |
| `lv3` | Level-3（Mode 5 Trap），挂起返回时 LP 已被驱逐；默认路由（含 DEF-30 的时长条件） |
| `lv3-strict` | Level-3，关闭短 CTA 路由（每个内核都可 Trap） |

指标：HP 端到端延迟（到达 → 结果就绪）P50 / P90 / P99；挂起时长；LP 吞吐（占独占吞吐的比例）；HP 占空比。

### 2.3 解读

- **OBS-16（共驻）**：native 的高优先级流不能抢占已经驻留的 CTA，但 GPU 会把 HP 的 CTA 调度到 LP 留下的空位上。cuBLAS GEMM 的波与波之间、部分占用的持久化内核、SDPA 都留有空位，所以 native 的小 HP 请求 P99 只有 0.7–1.8 ms（5060），与 LP 内核时长基本无关。**只有 LP 把 SM 占满时**（`persistent-full`），native 才退化为“等 LP 的 CTA 结束”，HP P99 = 12.7 / 26.6 ms（5060，LP 单核 12 / 29 ms），5080 为 4.0 / 9.2 ms（小 HP）和 8.6 / 19.4 ms（大 HP）。这说明 Level-3 的价值不在“比 native 快一点”，而在**最坏情况有界**：无论 LP 是什么内核、跑多久，HP P99 都在 1–2.6 ms 内。
- **Level-1 不能替代**：`lv1-sync` 的 HP 延迟就是在飞 LP 内核的剩余时长，随 LP 内核线性增长（5060 SDPA 32768：P99 368 ms）；`lv1`（不等在飞命令）与 native 相同，因为在飞内核照样占着 SM。
- **LP 吞吐**：Level-3 下 LP 保留独占吞吐的 0.83–0.99（大 HP 请求时 HP 占空比更高，上限是 `1 − HP 占空比`）。
- **大 HP 请求**：HP 自己的执行时间（约 2 ms）成为下限，Level-3 的 HP P50 = 2.1–2.4 ms，接近独占 1.99 ms。

### 2.4 RTX 5060 Level-3 尾延迟与 DEF-30

初次扫描中，5060 上 Level-3 在 cuBLAS GEMM、SDPA 负载上的 HP P99 为 2.5–3.2 ms，反而高于 native。A/B（每组 30 次到达）：

| 配置 | GEMM 6144 挂起 P99 / HP P99 | SDPA 16384 挂起 P99 / HP P99 |
|---|---|---|
| 默认（只按波数的短 CTA 路由） | 1.94 / 2.51 ms | 2.53 / 3.16 ms |
| 关闭短 CTA 路由 | 0.58 / 1.14 ms | 0.52 / 1.48 ms |
| HP 间隔再加 20 ms | 2.38 / 2.83 ms | 2.52 / 3.08 ms |

加大间隔不变，排除了“上一次恢复尚未完成”的假设；关闭路由后尾延迟消失。根因：LP 每次迭代的校验内核（37.7 M 元素的 `ne` / `any` / `logical_or`，各约 0.3–0.6 ms）是 loop-free 且满足 `[2, 1024]` 波，被路由到 Level-1；挂起到达时若它们排在被 Trap 的内核之后，挂起要等它们执行完。

修复（DEF-30）：短 CTA 路由增加**实测时长**条件（`XSCHED_SM120_SHORT_CTA_MAX_US`，默认 200 µs）。每个候选（函数, CTA 数, 线程数, 动态共享内存）的第一次发射留在 Level-3 并用 CUDA 事件计时，以后的发射只有时长 ≤ 200 µs 才走 Level-1。修复后 GEMM 6144 / SDPA 16384 的挂起 P99 = 0.22 / 0.25 ms，HP P99 = 0.84 / 0.85 ms；路由目标算子（`transpose_copy`、`gelu_tanh`、`softmax`、`layernorm`、`embedding` 等）稳态开销与只按波数时相同（−1%–+1%），超过 200 µs 的 `rope_apply` 留在 Level-3（+7%，关闭路由 +9%）。表 2.2 的 `lv3` 列即修复后的默认配置。

实现中的一个错误（T-25）：计时请求在提交时登记，事件在发射线程中才 record，而**从未 record 过的事件 `cuEventQuery` 返回成功**、`cuEventElapsedTime` 返回 `CUDA_ERROR_INVALID_HANDLE`。第一版因此把所有内核判为“长”，相当于关闭了路由（路由统计里 `lv1_short_cta` 为 0 才暴露）。现在只有 `recorded` 标志置位后才查询。

## 3. CUDA Graph 图内抢占（DEF-09，第一梯队 1）

实现原理见原理文档 §5.1：实例化时遍历图（拓扑序、子图内联、参数字节拷贝），Level-3 队列上的 `cuGraphLaunch` 改为逐节点提交，每个内核走正常的 Level-3 路径；图被修改即失效、整图发射。

### 3.1 结果

| 测试 | 不展平（图边界） | 展平（默认） |
|---|---|---|
| `test_graph_preempt_p35.py`：MLP 8 层 2048 维前向 + 反向 + `capturable` AdamW 整网捕获，40 次重放、15 次挂起，RTX 5060 | 挂起 P50 / P99 **289 / 407 ms**（3 次挂起即跑完），比特一致 | 挂起 P50 / P99 **0.13–0.20 / 0.38–1.39 ms**，HP P99 0.89–1.65 ms，参数 + 梯度 + 优化器状态**比特一致** |
| 同上，RTX 5080 | — | 挂起 P50 / P99 0.08 / 0.40 ms，比特一致 |
| 无抢占重放时间（5060） | 26.7 ms | 27.1 ms（+1.3%） |
| `DNN-07` `torch.compile(mode="reduce-overhead")` | 挂起 10–31 ms（Phase 3.3） | 3/3 通过，挂起 0.09–0.78 ms，`max_err=0` |
| `HW-04` 4 节点手工图（22 ms） | 挂起 20 ms | 挂起 0.19–0.20 ms，“preempted inside the graph” |

按时长展平（`XSCHED_CUDA_GRAPH_FLATTEN_MIN_US`）：阈值 1 ms 时该 27 ms 的图首发整图计时后被展平（挂起 P99 0.38 ms）；阈值 100 ms 时保持整图（挂起 P99 409 ms）。第一次实现同样踩到 T-25（事件尚未 record 就查询），现在先确认结束事件的 XQueue 命令已发射。

### 3.2 代价（OBS-17）

展平把一次 `cuGraphLaunch` 变成 N 次 XQueue 提交。每个节点约 5 µs CPU（提交 + Level-3 发射准备 + 驱动发射），而整图发射摊到每个节点不到 1 µs。GPU 时间远大于 CPU 时间时代价被隐藏（训练步 +1.3%）；小模型 decode（每步约 380 个微秒级内核）则受 CPU 限制（§4）。`XSCHED_CUDA_GRAPH_FLATTEN_MIN_US` 用来只展平长图。

## 4. vLLM 与 7B 模型（第一梯队 3）

### 4.1 环境与测试方法

- RTX 5080：独立 venv 安装 vLLM 0.34.0（torch 2.14.0+cu130，含 `sm_120`），模型 Qwen2.5-0.5B-Instruct、Qwen2.5-3B-Instruct（BF16）、Qwen2.5-7B-Instruct-AWQ（AWQ-Marlin，5.2 GB）。服务器无法直连模型仓库，经镜像下载。
- 测试脚本 `test/sm120_v2/eval/test_vllm_lv3_p35.py`：in-process 引擎（`VLLM_ENABLE_V1_MULTIPROCESSING=0`），vLLM 的计算流绑定到一个 XQueue；完整预热后先测无抢占生成（吞吐），再在生成期间由抢占线程随机 `XQueueSuspend(xq, 1)` → 高优先级流上执行 4 次 4096×4096 BF16 GEMV 链（独占 0.2 ms）→ `XQueueResume`。32 条请求、贪心解码，输出必须与 native 运行完全一致。prefill 为主的负载把提示词加长约 1,500 token、每条只生成 16 token。
- OBS-18（测试方法）：vLLM 维护自己的线程局部“当前流”（`vllm.utils.torch_utils.current_stream()`），第一次调用时若未设置就新建一个流并切换过去。0.5B 模型碰巧沿用了我们的流，7B 模型则没有：7B 的稳态 decode 全部绕过了 XQueue（挂起 ≈ 0 ms、各模式吞吐相同才暴露）。脚本现在先导入 vLLM（它会替换 `torch.cuda.set_stream`），再设置 XQueue 流，并断言 `model_runner.main_stream` 就是 XQueue 流。

### 4.2 发现与修复的问题

**DEF-29（跨流事件等待阻塞调用线程，P1 性能）**。最初 Level-1 下 0.5B decode 吞吐 −22%（11,360 vs 14,579 token/s）。调大在飞阈值、自旋预算、关闭直接提交都无效；cProfile 显示 native 每步在 `Event.synchronize` 上 0.31 ms，Level-1 每步在 `Event.wait` 上 **1.8 ms**：vLLM 的 `copy_stream.wait_stream(main_stream)` 让普通拷贝流等待 XQueue 上 record 的事件，原实现让调用线程阻塞到事件完成，把 vLLM 的 CPU 调度与 GPU 执行串行化了。修复见原理文档 §5.2：录制队列为 Level-1 时等 record 命令发射后用原生 `cuStreamWaitEvent`；Level-2/3 时把等待流提升为内部 Level-1 XQueue，由它的发射线程等待。修复后 Level-1 吞吐恢复到与 native 相同（0.5B 14,567 vs 14,579；7B 3,944 vs 3,943 token/s）。

**被否决的设计：GPU 等待主机标志（死锁）**。第一版让等待流 `cuStreamWaitValue32` 一个由桥线程写入的主机标志。合成测试全部通过，但 vLLM 在启动时卡死：`cuModuleLoadData` 持有驱动锁等 GPU 空闲 → GPU 在等标志 → 标志在等 record 命令完成 → 该命令卡在发射线程的 `cuLaunchKernel` 上等那把锁（`gdb` 线程栈确认）。教训：GPU 端的等待不能依赖“未来的主机端发射”。回归新增 `SYN-event-bridge-modload`（每次等待后立即加载新模块）。

**DEF-31（Lv3 恢复会重放非 killable 命令，P1 正确性）**。`Reactivate()` 的“无驱逐”分支按 `active_kernel_idx` 之后的日志全部重新发射，但只有 killable 内核会更新这个下标：整图、Level-1 路由内核、拷贝排在一个已经结束的 killable 内核之后时会被执行第二次。现在恢复时只重发 killable 内核和幂等命令（事件 record）。由代码审查与 vLLM 跟踪（恢复时下标指向日志之外）发现；合成复现用例 `test_graph_relaunch_p35.py` 未能单独触发它，作为防护保留并纳入回归。

**DEF-32（整图发射的内核节点继承过期的 Mode 5 参数窗口，P0 静默数据错误）**。DEF-29 修复后，vLLM 在 Level-3、不展平时**每次抢占后的输出都错**（0.5B 0/32、7B 0/32，无抢占时 32/32），展平时正确。`XSCHED_SM120_TRACE_LAUNCH=1` 跟踪显示恢复时 `active_idx=4231` 而日志是 6157–6167、`drained=35832`：图里的内核被当作很早以前的第 4231 号 Mode 5 发射驱逐 / 在入口排空，而整图不是 killable 命令，这些 CTA 永远不会恢复。原因：Guardian 参数窗口（`cuXtraSetDebuggerParams`）是**每个函数**的状态，图的内核节点在**图发射时**使用该函数当时的窗口；vLLM 里同一个 cutlass GEMM 既在预热时以 killable 方式 eager 发射，又在 decode 图里，于是之后每次整图重放都带着那次 eager 发射的窗口。异步等待让 vLLM 流水更深，挂起更常落在图执行期间，问题才暴露。

修复：实例化时记录每个图的全部内核函数（不论是否可展平）；Level-3 队列整图发射前、以及普通流上的透传整图发射前（若有任何函数持有 Mode 5 窗口），在上下文 `LaunchMutex` 下清零这些函数的窗口再发射，保证中间不会插入 Mode 5 发射。验证：0.5B 不展平 32/32（3 次）、7B 32/32、跟踪中恢复下标都在日志内、排空 CTA 从 35,832 降到 8。曾尝试“捕获开始时清零所有窗口”，无效（节点不在捕获时固化窗口），已删除。

**T-26（测试方法）**：PyTorch 流池中的流是 non-blocking 的；在默认流上生成输入后直接在另一条流上计算，会与 `randn` 竞争。GPU 有争用时这使 `test_event_bridge_p35.py` 的金标准本身不确定，整个进程“30/30 损坏”，一度误以为是新路径的错误。现在生成输入后先同步，并在报告中输出 native 确定性检查。

### 4.4 解读

- **Level-3 + 展平**给出最低的 HP 尾延迟：7B prefill P99 1.4 ms（native 4.1、Level-1 9.6），7B decode 1.1 ms（另一轮 2.6；native 3.4、Level-1 7.2）。0.5B decode 与 3B prefill 的 native 已经很低（0.5 ms，共驻，OBS-16），Level-3 与之相当（0.96 / 0.60 ms）。
- **Level-1** 的挂起要等在飞的整个 decode 步 / prefill 块，HP P99 是 native 的 2–3 倍：在单进程、同优先级流共驻的场景里，Level-1 反而比不用 XSched 更差。
- **Level-3 不展平**时整图仍是 Level-1 边界：吞吐几乎无损（0.5B −8%、7B −4%），但 HP P99 与 Level-1 同级。
- **吞吐代价**：展平的每节点 CPU 开销（§3.2）。0.5B decode（CPU 受限）−36%，7B decode −20%，7B / 3B prefill −11% / −16%。Level-1 吞吐与 native 相同（DEF-29 修复后）。降低它的方向：更轻的 Level-3 发射准备、或用 `XSCHED_CUDA_GRAPH_FLATTEN_MIN_US` 只展平长图（7B decode 的图本身就长于 2 ms，此阈值下仍被展平）。
- 本节是单进程测试（HP 与 vLLM 在同一进程、同一 GPU 上下文）。跨进程部署（HP 与 LP 两个进程、GPU 在上下文间时间片轮转，不能共驻）下 native 的 HP 延迟会大得多（Phase 3.4-2：native TPOT P99 数倍于 solo），那是 XSched 跨进程调度的场景，vLLM 的跨进程测试列为后续工作。

## 5. 收尾回归中的发现

**DEF-33（进程退出时的堆损坏，P1）**。RTX 5080 全量回归中 `S4-LIB-12`（cuFFT 2D R2C→滤波→C2R）以 `malloc(): invalid size (unsorted)` 中止；单独重复 18/20 次失败，RTX 5060 0/20。关闭本阶段的各项新功能均无效；用提交版本 f29aab3 的库与测试程序复测同样失败（5–6/8），而 Phase 3.4 的回归中它一直通过，说明是潜在缺陷，失败率随环境变化。`gdb` 栈：中止发生在**进程退出**的静态析构中——`~Sm120TrapEngine` → `RestoreOriginal()` → `Sm120Arena::RestoreAll()` → `cuXtraMemcpyHtoD` → libcuda 的 `calloc`。引擎表（每上下文一个）从不删除条目，只在静态析构时销毁；此时 CUDA 运行时 / cuFFT 的退出处理可能已经拆除了上下文，向其 ToolsMemory 写回原处理程序就成了 libcuda 内部的释放后使用。测试的计算结果本身一直正确（`stdbuf` 输出 `max_err=0`），只是退出码 134。

修复：Trap 处理程序位于每个上下文自己的 ToolsMemory 中，上下文销毁时由驱动回收，退出时恢复没有意义。每上下文的单例表（Trap 引擎、Guardian 注册表、`LaunchMutex` 表）以及图计划表改为有意泄漏的堆对象，进程退出时不再从静态析构中调用驱动。修复后 LIB-12 路由关闭 0/20、开启 0/10，Suite 4 全部通过。

**OBS-20（开放）**：5060 两次全量回归中共有 3 个进程在**刚启动时**出错，且都紧跟在一个带抢占的 Level-3 进程之后：两次 native 金标准本身不确定（尚未创建任何 XQueue；`S7-cumsum_64m-lv3m5` 的整数 cumsum 两次结果不同），一次启动约 1 s 内 Xid 43 + 719（`S7-linear_bwd_accum-lv3m5`）。受控复现（Level-3 进程退出后立即启动探针 `probe_native_det_p35.py`，探针分别以纯驱动和经 shim 透传运行）0/54。DEF-33 表明 Level-3 进程退出时会向已拆除的上下文写入；这可能也是 OBS-20 的原因，但尚未证实。DEF-33 修复后的 5060 全量回归（295 项）中未再出现（§7）。

### 8.1 端到端：两个 vLLM 进程，XSched 透明调度

`bench_vllm_mp_p35.py`：HP 进程是 Qwen2.5-0.5B（泊松到达的短对话请求，每个 16 token），LP 进程是 Qwen2.5-7B-Instruct-AWQ 或 3B（prefill 为主的长文档批次，每批与参考输出比较）。`glb-*` 模式下两个进程都只设环境变量：`XSCHED_SCHEDULER=GLB`、`XSCHED_AUTO_XQUEUE=1`（HP Level-1 优先级 1，LP Level-1/3 优先级 0），`xserver` 用 HPF 策略，vLLM 不改一行代码。

第一次运行 `glb-lv3`：LP 1/11 批输出错误，HP 端到端延迟比 native 还差（E2E P50 79.8 ms、TTFT 13.2 ms），并伴有就绪门控超时。依次定位并修复了三个问题：

| 编号 | 现象 | 根因 | 修复 |
|---|---|---|---|
| **DEF-36** | LP 结果错误、HP 变慢、门控超时 | 自动 XQueue 为每个创建的流建队列；PyTorch 每个优先级预建 32 条池流，每个 vLLM 进程 **128 个 XQueue**。每个 HP 请求 `xserver` 挂起 LP 的全部 128 个 Level-3 队列，而 **空闲队列也会发 BAR0 脉冲**（`Interrupt()` 只在最后一个内核不可 Trap 时跳过）。全 GPU 的脉冲风暴打到 HP 自己的线程束上，并可能落在同进程另一队列的恢复波次中 | 自动 XQueue **在流第一次提交时才创建**（`XSCHED_AUTO_XQUEUE_LAZY`，默认开）；**空闲队列不发脉冲**（发射线程已暂停，`cuStreamQuery` 显示流空闲即跳过）。之后 LP 0 错、HP P50 33.6–39.7 ms |
| **DEF-37** | 3B LP 时 HP 仍 46 ms（独占 30.5），调大恢复延迟、改功耗都无效 | 新增的 shim 计数显示 LP 的 **46% 命令在传统默认流上**（vLLM 的 model runner 用了默认流）。默认流永远绕过 XSched：LP 的 XQueue 挂起后这些工作照常运行，GPU 在两个上下文间时间片轮转 | 自动 XQueue 模式下默认流上的异步工作转到每个上下文一个**阻塞的代理流**（有 XQueue，`XSCHED_AUTO_XQUEUE_LEGACY`，默认开）；57 个同步拷贝 / 置零 API 先排空阻塞队列（代理在内）再调用驱动；代理是阻塞流，驱动仍按传统流语义与之排序。应用一旦创建自己的阻塞流（传统流与阻塞流之间有隐式同步，代理流没有），默认流工作就回到原路径 |
| （优化） | 每个 decode 步之间 HP 短暂空闲，LP 被反复恢复 / 挂起 | HPF 无迟滞 | 新增 `XSCHED_HPF_RESUME_DELAY_US`（默认 0）：高优先级队列在该时间内就绪过时，低优先级队列保持挂起。DEF-37 修复后不再需要，默认不启用 |

最终构建（含 DEF-38 / 39 / 40 / 41）复测：3B LP `glb-lv3` HP E2E 29.9 / 31.8 ms、LP 91.1%；7B-AWQ LP `glb-lv3` 30.1 / 30.9 ms、88.3%；`glb-lv1` 33.8 / 39.3 ms（3B）、49.6 / 66.2 ms（7B）；全部一致。DEF-40 只在进程启动、尚未登记的约 100–200 ms 内暂停脉冲。

LP 的命令全部经过 XQueue（传统流 0 条、无队列的流 0 条），门控超时 0 次。HP 达到独占延迟，LP 保留约 90% 吞吐；Level-3 的尾延迟明显好于 Level-1。7B-AWQ 的 Marlin GEMM 无法 Trap（DEF-34），所以其 P99 略高于 3B。

### 8.2 DEF-34：寄存器文件被分配满的 SM 不接受 Trap（硬件限制）

在追查一个合成测试时发现：255 寄存器 × 128 线程 × 每 SM 2 个 CTA 的内核在 1,600 多次挂起中**一个 CTA 都没被驱逐**。逐项排除：

| 配置（每 SM） | 已分配寄存器 / 65,536 | 驱逐 |
|---|---|---|
| 168 寄存器 × 128 线程 × 2 CTA | 43,008 | 41/52 |
| 192–210 寄存器 × 2 CTA | 49,152–55,296 | 43–49 / 64–66 |
| 240 寄存器 × 2 CTA | 61,440 | 56/82 |
| 248 寄存器 × 2 CTA | 63,488 | 57/81 |
| 168 寄存器 × 3 CTA | 64,512（空闲 1,024） | 45/59 |
| 252→256 寄存器 × 2 CTA | **65,536（空闲 0）** | **0/61** |
| 254→256 寄存器 × 1 CTA | 32,768 | 46/60 |

规律：**SM 的寄存器文件分配到最后一个寄存器时，Trap 不被接受**（与每线程寄存器数无关；同一内核每 SM 1 个 CTA 时正常驱逐）。这类内核的 Level-3 挂起实际退化为等内核结束；数据正确（108 次运行 0 错）。Suite 7 的 49 个内核中只有 `int8_mm` 的 cutlass INT8 GEMM 如此；vLLM 中有 Marlin AWQ GEMM（255 × 8 线程束 × 1 CTA）、`_topk_topp_kernel`、`_penalties_kernel`。现在按几何形状检测（占用率 × 线程束 × 每线程束分配，粒度 256），计入路由统计 `rf_full`，首次出现时记一行日志；`XSCHED_SM120_RF_FULL=lv1` 可把它们显式路由到 Level-1。单 CTA 就占满寄存器文件的内核（如 Marlin）无法靠降低占用率修复。

### 8.3 DEF-38 / DEF-39：同一进程内多个 Level-3 队列与 GPU 卡死

`test_multiqueue_lv3_p35.py`：一个进程中 4 条流各有一个 Level-3 XQueue，每条流做 3,000 步原地 `addmm_`（重复执行或恢复不完整都会改变结果），每个队列各有一个线程随机挂起 / 恢复它（间隔 0.3–1.7 × 600 µs，保持 150 µs；合计约 6,600 次脉冲 / 秒）。

| 构建 / 配置（RTX 5080，4 队列） | 结果 |
|---|---|
| 修复前（2 队列：0/8） | **5/8 次挂死**（GPU 100%，所有线程停在 `cuStreamSynchronize`） |
| 门控关闭（DEF-38 / DEF-39 / DEF-40 各构建） | 1/4、5/8、2/3 挂死（合计含修复前 **13/23**） |
| 只串行化、不等待恢复（`XSCHED_SM120_CTX_PULSE_GATE=2`） | **10/10 通过** |
| **门控开启**（DEF-38 → DEF-40 各构建） | **26/26 通过**（约 92,000 次挂起；每次运行墙钟时间不变） |

RTX 5060 上同样的测试触发 Xid 109，桌面随之冻结（见 8.4）。

**定位**：gdb 栈只能说明主机线程都在等 GPU。新增的看门狗（`XSCHED_SM120_WATCHDOG_MS`）在卡死时不加锁地经私有流读出每个队列的控制头：三个队列停在 `PreemptStream` 第 4 阶段——`cmd=5` 已写入控制头，但门控镜像的写入没有完成，脉冲还没发出（其中两个 `evicted=0`）；第四个停在 `ResetControlSync`。第三个队列 `evicted=54` 却从未自己发出脉冲：它的 CTA 是被别的队列的脉冲驱逐的。

**CE 与 SM**（`kernels/ce_vs_sm_probe.cu`，原生 CUDA，所有 SM 被自旋 CTA 占满）：

| 操作 | SM 全满时 |
|---|---|
| 主机↔设备拷贝（4 B–1 MB）、pitched 2D 主机→设备拷贝 | 完成（拷贝引擎） |
| `cuMemsetD8/D32Async` ≤ 4 KB | 完成 |
| `cuMemsetD2D32Async`（跨步）、`cuMemsetD8Async` 32 KB / 1 MB、`cuMemcpyDtoDAsync` | **阻塞**，直到有 SM 空出（驱动用 SM 内核实现） |

门控镜像正是用跨步 memset 写的。**机理**：脉冲同时打断一个 SM 上的所有线程束，各自读本队列的 cmd。队列 B 的脉冲恰在队列 A 的 cmd 写入落地时到达，A 的同一 CTA 中一部分线程束读到 0（返回用户代码、停在用户 `BAR.SYNC`），一部分读到 5（停在处理程序的 `BAR.SYNC.TRAP`），CTA 卡在 SM 上。A 写镜像的 memset 因此拿不到 SM，A 的脉冲与恢复脉冲都发不出去。单队列协议（先写 cmd、同步、再发脉冲）在多队列下不再成立。

**修复**：
- DEF-38：引擎级脉冲互斥（`PreemptStream()` 整段、`PrepareRestore()`），发脉冲前等待同上下文其他队列的 Mode 5 恢复完成（`XSCHED_SM120_CTX_PULSE_GATE`，默认开）。
- DEF-39：门控镜像改为 pitched 2D 主机→设备拷贝，控制块复位改为主机→设备拷贝且只清发射过的 CTA 范围，未发生脉冲 / 恢复时跳过（`XSCHED_SM120_CE_CONTROL`，默认开）。这也去掉了每次挂起前“等某个 SM 有空位”的隐性延迟。门控关闭时只有 DEF-39 并不能解除卡死（恢复脉冲已能发出，但流仍不结束），所以门控是必要的。

### 8.4 DEF-40：脉冲会打断 XSched 之外的上下文（安全缺陷）

本轮在 5060 上反复出现桌面进程的 Xid 31（`MMU Fault … GPCCLIENT_GCC faulted @ 0x0`），一次 Xid 109 让桌面冻结、整机重启；共享的 5080 上另一用户的作业在测试中途启动时也出现了 Xid 109。假设：脉冲打断的是发出时驻留在 GPU 上的上下文，没有 XSched 处理程序的上下文无法返回。受控验证（`test_foreign_ctx_p35.py`，只用自己的进程、GPU 空闲时）：

| 运行（RTX 5080） | 原生受害者进程 |
|---|---|
| 对照：无挂起 | 15 s 5,028 次迭代，无误 |
| Level-3 高频挂起（约 7,000–8,000 次 / 15 s） | **2/2 次被杀死**：`CUDA error: unspecified launch failure`，受害者通道 Xid 109 |

修复：任何级别的 XQueue 都为其上下文安装处理程序并登记为租户；NVML 每 100 ms 检查 GPU 上的进程，存在未登记的进程时不发脉冲，挂起退化为 Level-1（原理文档 §9.9）。在 5060 桌面上，默认配置下脉冲即被禁止（日志列出 gnome-shell、Xwayland、nautilus、ghostty），测试按 Level-1 语义通过、无 Xid。

### 8.5 DEF-41：两个同时运行 Level-3 的进程

`test_multiqueue_lv3_p35.py --procs 2 --queues 2`：两个进程各有 2 个 Level-3 队列，同步开始各自的挂起压力。主机级脉冲锁关闭 6/6、开启 8/8 次运行，每次都有一个进程收到 Xid 109 `CTX SWITCH TIMEOUT`（随后 CUDA 719、进程 SIGSEGV），另一个进程结果正确。两个进程是两个分时的上下文：时间片切换恰在一方的线程束处于 Trap 处理程序中时到达即超时——DEF-27 的机理。就绪门控让 HP（Level-1）进程等 LP 挂起完成才发射，所以 HP + LP 的形态安全；两个对等的 Level-3 进程之间没有这种关系，串行化脉冲也无法阻止上下文切换。缓解：运行 Level-2/3 内核的进程在租户登记中加 `.lv3` 标记，GPU 上有另一个 Level-3 进程时不发脉冲（两者都退化为 Level-1 语义；`XSCHED_SM120_LV3_PEERS=allow` 放行）。

### 8.6 其他

- **DEF-35**：SASS 循环检测只识别 `BRA`（`0x947`），漏掉带统一谓词的 `BRA.U`（`0x547`，如 `BRA.U UP0, target`），这类循环被判为 loop-free。已修复（偏移字段布局相同，用已知目标的三条分支验证）。Suite 7 的 49 个生产内核分类不变。
- **DEF-20b 结案（不可达）**：255 寄存器内核的 `R254` 不保存，但 ptxas 在 sm_120 上**从不分配 R253 / R254**——报告 255 寄存器的 272 个 PyTorch flash 内核与合成内核的最高寄存器都是 `R252`。曾实现的 `R254` 保存已撤回（会写一个保留寄存器）。
- **OBS-21**：交替 A/B（当前构建 vs 提交版本 f29aab3）各 30 次 `S8-prefill-lv3-slo`，共 9,635 个 LP 迭代 0 错；出错的那次运行 TTFT P99 异常（50 ms），同时段无任何驱动事件。累计约 1/12,000 次迭代，原因未定，保留在回归中观察。
- **显示 GPU（OBS-14 扩展）**：RTX 5060 驱动桌面，高频抢占时桌面图形上下文的时间片切换偶尔撞上处于 Trap 处理程序中的线程束，出现 Xid 109（`CTX SWITCH TIMEOUT`，进程 719）。本轮 5 次，全部在压力测试中（约 6,600 次脉冲 / 秒的多队列测试、11,000 次 / 秒的 flash 压测、`SYN-stress-g8`），桌面终端同时出现 Xid 31。与 DEF-27 同一机理，但另一方是不受 XSched 管理的桌面，就绪门控无法协调。无显示的 RTX 5080 全天无新增 Xid。建议 Level-3 部署在无显示的 GPU 上。
- **T-26（又两次）**：`test_regpress255` 中 `out.zero_()` 在默认流上执行、与非阻塞流上的内核竞争，造成“整批错误”的假象；跟踪显示该批次根本没有任何驱逐，才定位为测试问题。

## 9. 局限与后续

- vLLM 跨进程（两个 vLLM 进程，GLB 调度，自动 XQueue）已打通（§8.1）；SGLang 尚未测试。
- DEF-34（寄存器文件被分配满时 Trap 不被接受）是硬件限制，只能检测与改路由；vLLM 的 Marlin AWQ GEMM 受影响。
- DEF-38 跨进程只做串行化（主机级 `flock`）；两个同时运行 Level-3 的进程不受支持（DEF-41，默认不发脉冲）。更彻底的方案需要让同一 GPU 上的 Level-3 进程不同时驻留（例如由 `xserver` 让对等 LP 进程轮流运行），或共用一个上下文（MPS，未验证）。
- DEF-40 的外来上下文检测是轮询（100 ms）：外来进程刚启动的一瞬仍可能被脉冲打到；同一进程中没有 XQueue 的其他上下文不受保护。
- 驱动 GPU 显示的卡（RTX 5060）上高频抢占会让桌面上下文的时间片切换撞上 Trap 处理程序（Xid 109）；Level-3 应部署在无显示的 GPU 上。
- 展平的 CPU 开销：小模型 decode 仍有 −36%；可选方向是批量提交（一次 XQueue 提交携带整个图的节点序列）与更轻的 Level-3 发射准备。
- 手工构造的图若在实例化后用 `cuGraphExec*SetParams` 换了内核函数，函数列表会合并记录；`cuGraphExecUpdate` 按新图重新收集。条件节点、主机节点等仍使整图不可展平（整图发射，DEF-32 的清零仍然生效）。
- 第一梯队 4（驱动版本鲁棒性自检）未开始。
